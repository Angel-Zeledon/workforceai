AI Workforce OS Architecture

AI Workforce OS separates deciding from doing: a Go backend is the source of truth, a Python runtime only reasons with the LLM, and a Next.js frontend draws the office from events. This page explains how the pieces fit and how a request travels end to end.

Components

The system is five processes plus an optional proxy. All business state lives in the backend; the runtime keeps no state between calls.

Backend and runtime boundary

The core rule: the runtime never talks to Postgres, Redis or external systems. It receives a task with its context and returns a result, tool requests and usage; it only contacts the LLM provider. The backend decides permissions, autonomy and budget, and executes the tools.

The backend calls the runtime over HTTP with JSON. If RUNTIME_TOKEN is set on both sides, calls carry that shared secret. The AI engine sits behind an interface of its own, so CrewAI can be replaced without touching the backend.

Request flow

A request follows this path: the user's ask reaches the orchestrator, which asks the runtime for a plan, validates it and creates tasks; each task is assigned to an agent that uses tools, sensitive actions wait for human approval, and a report is synthesized at the end.

  1. The user submits text with POST /api/v1/requests (or through chat, which routes it). The backend answers 202 with request_id and emits request.received.
  2. The orchestrator asks the runtime for a plan. The backend validates agents, dependencies and limits before accepting it, then emits plan.created and task.created.
  3. Tasks run respecting depends_on. Each one changes the agent state (agent.state_changed) and may trigger agent consultations (message.sent) and a quality review (task.reviewed).
  4. Tools requested by the runtime go through the autonomy policy and permissions. If approval is needed a pending record is created and the task enters awaiting_approval.
  5. A user with permission decides with POST /api/v1/approvals/{id}/decision. The task resumes or is blocked.
  6. When all tasks finish, the runtime synthesizes the report; the backend emits report.created and request.completed.
  7. In parallel, per-request cost is recorded and the budget is enforced: budget.warning and budget.exceeded can pause execution.
POST /api/v1/requests {"text": "..."}      -> 202 {"request_id": "..."}
  orchestrator -> runtime POST /v1/plan          -> tasks + depends_on
  backend validates the plan                     -> plan.created, task.created*
  per task: runtime POST /v1/run-task            -> output, consults, tool_requests, usage
  tool_requests -> policy/autonomy check         -> approval.requested (if needed)
  POST /api/v1/approvals/{id}/decision           -> approval.resolved, task resumes
  runtime POST /v1/synthesize                    -> report.created, request.completed

Realtime channel

GET /ws opens one WebSocket per organization. The backend publishes each event to Redis (channel aiworkforce:events) and a hub forwards the frame only to clients whose org_id matches; a frame without org_id is dropped. Without REDIS_URL the hub receives events locally.

On connect a hello event carries the agent list, followed by domain events. The server pings every 30 s, closes if no pong arrives within 60 s and drops slow clients (256-frame queue). With authentication on, the socket closes with code 4401 when the token expires so the client reconnects. There is no replay: after reconnecting, the client reloads state over REST.

Multi-tenancy

Each account creates its own organization and the org_id travels inside the access token; it is never taken from client input. The HTTP layer puts it in the request context and every query is filtered by it.

As defense in depth, Postgres enforces row-level security. Each transaction sets app.org_id with set_config and the policies read that function; if the value is missing, queries return no rows (fail closed). The application connects with a non-owner role (DB_APP_ROLE, default app_user, without BYPASSRLS), and migrations use a separate connection (MIGRATE_DATABASE_URL). The WebSocket hub also filters by organization.

Simulation versus real AI

The runtime's HTTP contract is the same in both modes; the engine changes. In simulation (the default, with no key or with SIMULATION=true) the runtime returns scripted results with simulated latencies, with no network and no cost. In live mode it uses the configured provider and the runtime's GET /healthz reports mode: live and the provider.

If a provider is configured but the live engine cannot start, the runtime answers in simulation with status degraded and a warning; there is no silent fallback. The backend reflects the mode in its own /healthz as runtime_mode.

Tip. SIMULATION=true always wins: no network calls are made even when keys are present.

Deployment and edge

docker-compose.yml starts postgres, redis, object storage, agent-runtime, backend and frontend; demo and production variants exist. In production Caddy terminates TLS, adds security headers and routes by path: /api/* and /ws to the backend, everything else to the frontend. Agent code execution uses a separate sandbox image and runner.
