Authentication and multi-tenancy

AI Workforce OS can run open, with one fixed organization, or with accounts, roles and per-organization isolation. This page describes the auth service in the Go backend: how accounts and sessions work, what each role can do and how Postgres enforces the tenant boundary.

Two modes: AUTH_ENABLED false and true

With AUTH_ENABLED=false (the default) there is no login. The API is open and every request uses a single fixed demo organization. This is meant for local development and demos, and the server logs a warning at startup. Do not expose it to a network.

With AUTH_ENABLED=true the API requires a bearer access token on protected routes, resolves a role for every request and scopes every database access to the caller's organization. Startup validation refuses the configuration unless JWT_SECRET has at least 32 bytes, DATABASE_URL is set and ALLOWED_ORIGINS does not contain a wildcard.

# Auth enabled
AUTH_ENABLED=true
JWT_SECRET=<at least 32 random bytes>
DATABASE_URL=postgres://...         # required with auth
MIGRATE_DATABASE_URL=postgres://... # owner/DDL role, runs migrations
DB_APP_ROLE=app_user                # default
ALLOWED_ORIGINS=https://app.example.com   # no wildcard when auth is on
TRUSTED_PROXIES=10.0.0.0/8          # honour X-Forwarded-For for IP limits
AUTH_COOKIE_SECURE=true             # default; false only for plain-http dev
AUTH_COOKIE_NAME=wfai_refresh       # optional override

Accounts and registration

Registering creates a user, a new organization and an owner membership in one step, then opens a session. The organization starts with the default budget configured for new organizations. Email addresses are normalized (trimmed, lowercased) before any lookup or storage, so Ana@Example.com and ana@example.com are the same account.

Passwords are hashed with Argon2id (64 MiB, 3 iterations, 2 lanes by default). Hashes created with weaker parameters are re-hashed on the next successful login. Input is validated with these rules:

FieldRule
emailTrimmed and lowercased; max 254 characters; must parse as a plain address with a dot in the domain
password10 to 128 characters; not in a short common-password list; not equal to the email or its local part; not a single repeated character; at least two of lowercase, uppercase, digits, symbols
name1 to 100 characters, no control characters
org_name2 to 100 characters, no control characters; the slug is derived from it plus a random suffix

Login, lockout and rate limits

Login failures are counted per account. After five wrong passwords the account is locked for 15 minutes and further attempts return a locked error with the unlock time. Unknown emails are verified against a dummy hash so that a missing account costs the same time as a wrong password, which limits account enumeration.

Throttling is layered: a per-email limiter that does not depend on whether the account exists, and per-IP limiters on the unauthenticated endpoints. Counters live in Redis when available, so they survive restarts, and in memory otherwise. IP limits honour X-Forwarded-For only from addresses listed in TRUSTED_PROXIES. The defaults are:

LimitDefaultKey
Login attempts10 per 15 minEmail address (hashed), whether or not the account exists
POST /login20 per 15 minClient IP
POST /register and /invitations/accept5 per hourClient IP
POST /refresh and /logout60 per 15 minClient IP
Authenticated auth and invitation endpoints120 per minUser
Failed passwords before lockout5, lock for 15 minAccount

Sessions: access token and rotating refresh token

A session has two parts. The access token is a short-lived (15 minutes by default) HMAC-signed JWT carrying the user, the organization and the role, sent as a bearer token. The refresh token is an opaque random value, valid 30 days by default, stored server-side only as a SHA-256 hash and delivered in an HttpOnly, SameSite=Strict cookie (wfai_refresh) scoped to /api/v1/auth, with the Secure attribute on by default. It never appears in a JSON body.

Refresh and logout act on the ambient cookie, so they require the custom X-WFAI-CSRF header and reject cross-site requests by Sec-Fetch-Site and Origin. Each refresh rotates the token inside a family. Presenting an already-used token revokes the whole family, which detects theft. Logout revokes the family; logout-all revokes every refresh token of the user in every organization.

POST /api/v1/auth/login
Content-Type: application/json

{"email":"ana@example.com","password":"...","org_id":"(optional)"}

200 OK
Set-Cookie: wfai_refresh=...; Path=/api/v1/auth; HttpOnly; SameSite=Strict; Secure
{"token_type":"Bearer","access_token":"...","expires_in":900,
 "user":{...},"org_id":"...","role":"owner"}

Roles and permissions (RBAC)

Each membership has one role: owner, admin, member or viewer. A role is a set of permissions named resource:action, and each role is a strict superset of the one below. By default the role is re-read from the database on every request, so demoting or removing a member takes effect immediately instead of when the access token expires (the TrustTokenClaims option trades this for statelessness).

Role changes obey two rules. An owner can assign any role; an admin can assign and manage only roles below admin; nobody can grant a role above their own. The last owner cannot be removed. Agents never hold approval-granting permissions such as artifacts:approve.

RoleAdds on top of the role below
viewerRead-only: members, agents, tasks, requests, conversations, approvals, reports, memories, activity, metrics, artifacts, files, skills, shop
memberCreate requests and tasks, post in conversations, write memories, create/edit/comment/export artifacts, write files, write skills, buy in the shop, read connections
adminManage the organization, invite and manage members, write agents, manage tasks, decide approvals, read the audit log, manage connections and grants, pause and kill switch, approve/delete artifacts, delete files, review skills, delete conversations
ownerDelete the organization, billing, release the kill switch, edit approval policy (policy:manage)

Organizations, members and switching

A user can belong to several organizations, with a different role in each. GET /me returns the user and the list of organizations with names and roles. POST /switch-org opens a new session for another organization the user belongs to, and the previous refresh token should be dropped. Asking for an organization without membership returns forbidden.

Members are listed, added by email (an existing user), re-roled and removed within the actor's organization only; targets from other organizations are reported as not found. Removing a member also revokes that user's refresh tokens for the organization.

Invitations

Admins and owners create invitations for an email and a role they are allowed to assign. The server stores only the SHA-256 of the one-time token and returns the plaintext once, at creation. The server does not send email: the inviter shares the link, which the frontend serves at /invite. A new invitation to the same address revokes the previous pending one, and links expire after 7 days by default.

Accepting is public and takes the token. A new person provides a name and a password. An existing account must prove ownership with its current password, with the same lockout as login. Unknown, expired, revoked and used tokens fail without revealing which. If the inviter has since been demoted or removed, the invitation stops working. Creation, revocation and acceptance are written to the audit trail, storing only the email domain.

Tenant isolation with Postgres row-level security

Role checks decide what a user may do; row-level security decides which rows exist for them. Every tenant table has a tenant_isolation policy comparing org_id with app_current_org(), and FORCE ROW LEVEL SECURITY applies it even to the table owner. Each request runs in a transaction that starts with set_config('app.org_id', ..., true). The setting is transaction-local, so a pooled connection cannot carry one tenant into another request.

It fails closed: when app.org_id is unset, no row is visible or writable. The server connects with owner credentials and switches to app_user on every connection (DB_APP_ROLE), a role that is not a superuser, has no BYPASSRLS and owns no table. The audit log is append-only for that role (UPDATE and DELETE are revoked). Migrations run with the separate MIGRATE_DATABASE_URL.

-- One transaction per request, scoped to the caller's organization
SELECT set_config('app.org_id', '<org id>', true);   -- == SET LOCAL

CREATE POLICY tenant_isolation ON agents
  USING      (org_id = app_current_org())
  WITH CHECK (org_id = app_current_org());

Endpoint reference

The auth router is mounted at /api/v1/auth and the invitation router under the same prefix. Permissions are checked by middleware before the handler runs; the service re-checks the actor's current membership on every member operation.

EndpointAccess
POST /api/v1/auth/register, /login, /refresh, /logoutPublic (refresh and logout use the cookie plus X-WFAI-CSRF)
POST /api/v1/auth/invitations/acceptPublic, token in the body
GET /api/v1/auth/configPublic, reports whether auth and registration are enabled
GET /me, POST /logout-all, POST /switch-orgAny authenticated user
GET/POST/PATCH/DELETE /membersmembers:read, members:invite, members:manage; a member may remove themself
GET/POST/DELETE /invitationsmembers:read to list, members:invite to create and revoke

Email verification and trial accounts

With EMAIL_VERIFICATION=true, POST /auth/register creates the account but opens no session: it answers 202 with verification_required and sends a one-time link (random token, stored as a hash, valid for 24 hours). POST /auth/login answers 403 email_not_verified only when the password is correct; with a wrong password it still answers invalid_credentials, so the endpoint does not reveal which addresses exist. POST /auth/verify {token} consumes the link, marks the address verified and opens the session. POST /auth/verify/resend {email} sends the link again, rate-limited per address, and answers 204 whether or not the account exists.

With TRIAL_ENABLED=true, POST /auth/trial creates a throwaway account with its own organization and returns the username and a generated password exactly once (format XXXX-XXXX-XXXX); only its hash is stored. The account stops working after TRIAL_TTL_HOURS: the access token never outlives the trial, login answers 403 trial_expired and session renewal is refused. Creation is limited per client address and in total per day. GET /auth/config tells the UI about both features.
