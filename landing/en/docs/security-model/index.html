Security model

The design starts from one premise: a language model can be tricked, because it processes untrusted text and can act. So damage is bounded by deterministic controls in the backend (Go), not by prompt instructions. This page describes what is implemented and, at the end, what is not.

Design principles

Agents only produce tool requests. The backend decides whether they run, evaluating in order: role permissions, connection grants, limits, autonomy level and approvals. The agent runtime receives no credentials and cannot alter the identity under which actions are taken.

Effective authority is the intersection of what the originator of the work can do and what the agent can do. Delegation never widens power, and delegation depth is bounded (5 by default). Anything that fails or cannot be read is treated as denied (fail closed).

Tip. There is no promise that the model will never be influenced by malicious text. The promise is that the blast radius stays limited to what the backend authorizes.

Credentials vault

Connection credentials (OAuth tokens, API keys) are stored encrypted with AES-256-GCM in an envelope scheme: a key-encryption key (KEK) held outside the database wraps a per-organization data key (DEK), and the DEK encrypts each secret with a random nonce. The additional authenticated data includes organization, credential, version and kind, so a ciphertext copied to another row or organization does not decrypt.

Without a configured KEK (CONNECTIONS_KEK, 32 bytes in base64) the vault fails closed: it neither stores nor reads live credentials. Several KEKs can be loaded at once to rotate them, and credentials support rotation with active and retired versions. Revoking a connection suspends its use, calls the provider's revocation endpoint and destroys the ciphertext (crypto-shredding).

The model never sees a secret: the contract between the backend and the runtime has no credential fields, the API returns only metadata and a short hint, and exact secret values loaded in memory are registered with a redactor that masks them in logs, audit entries and outputs.

KEK (outside the DB, CONNECTIONS_KEK)
  └─ wraps → per-organization DEK (versioned)
       └─ AES-256-GCM(secret, random nonce, AAD = org|credential|version|kind)

Human approvals

An agent can request an action; it can never grant approval. Approvals are made by people with the admin or owner role, and the role is read from the session token, not from the request body. Each approval is bound by hash to the exact arguments approved, is consumed once and is revalidated before execution, because rules may have changed while it waited. It expires (48 hours by default) and an expiry counts as a rejection.

There is a floor that no organization rule can weaken: declared high risk, actions on the mandatory-approval list and agents at the suggest or approve_each levels. On top of it, an organization can add rules: amount thresholds, forbidden actions, new recipients, sensitive categories, required role by amount or action, and dual approval.

Dual approval requires two distinct humans holding the required role, the same person cannot approve twice and the person who made the request never approves. A single rejection from an authorized person is final. If the action runs after a server restart, the approval is claimed atomically so that it executes at most once.

Autonomy levelBehavior
suggestThe agent only proposes; nothing is executed.
approve_eachEvery action with an external effect waits for approval (the default level).
rulesRuns on its own if an allow rule matches and no deny rule does; otherwise asks for approval.
autonomousRuns without approval, except mandatory-approval actions, high risk or effects toward new recipients.

Least privilege for connections

An action through an external connection must pass three filters in series: the capability the provider declares, the grant the organization gives to a specific agent, and the policy and approval of the action itself. A grant can only narrow what the connection allows. The recommended pattern is to keep a read-only connection separate from a write one.

Each connection and each grant supports limits per minute, hour and day, writes per day, bytes per day and a monthly budget. These counters are computed from the usage table in Postgres, so they survive restarts. An agent cannot change its own autonomy, permissions or rules, and any deny rule beats an allow rule.

Spending caps, hours and anomalies

Before every runtime call, the maximum estimated cost is reserved against the request, the agent and the organization, and afterwards reconciled using the higher of the cost reported by the runtime and the one recomputed by the backend. When a cap is reached, the request or the agent is paused and a human decides whether to raise it. Structural limits also guard against loops: delegation depth, tasks per request, retries, time per task and per request, and a per-organization queue (8 concurrent calls by default).

Operating hours are a weekly schedule with a time zone that only prevents starting new work outside open hours; it does not block approvals or work already admitted. Anomaly detection v1 applies four explainable rules and records every finding in the audit log. On its own it never blocks; automatic freeze is optional and ships disabled.

RuleFires when
spend_spikeSpend in the current hour is at least 4 times the hourly average of the previous 24 h and at least 2 USD.
tool_request_burstAn agent requests 40 or more tools within 60 seconds.
rejected_approvals5 or more approvals are rejected within 1 hour.
new_recipient_domains3 or more never-seen recipient domains appear within 1 hour.

Kill switch and read-only mode

The kill switch has two levels. Any admin or owner can activate it; lifting it requires the release permission (owner) and a written reason. It can also be imposed with the KILL_SWITCH environment variable (freeze or lockdown), which no API call can lift: the variable must be removed and the configuration reloaded.

Beyond it there are per-agent pause (graceful lets the call in flight finish; immediate stops everything), read-only mode for the organization or an agent, and switching off a tool or a single action (for example email or email.send). In read-only mode agents keep reading and proposing, but effects are denied. Held actions return to the approval queue and must be approved again: nothing runs by inertia when a control is lifted.

Audit log

Audit is a per-organization hash chain: each entry includes the hash of the previous one (SHA-256 over a canonical representation with sequence, actor, action, entity and details). Changing, deleting, reordering or inserting an entry breaks the chain from that point, and truncating the tail is detected against the chain head. A verification endpoint recomputes the chain.

Before being chained, every entry goes through a scrubber that keeps metadata only: it replaces content fields (bodies, arguments, subjects, summaries) and credential-like keys with [redacted], masks embedded secrets and truncates long strings. Audited events include authentication, policy decisions, approvals, tool executions, and changes to controls and budgets.

GET /audit          # query
GET /audit/export   # JSONL or CSV
GET /audit/verify   # recomputes the hash chain

Tenant isolation, authentication and limits

Tables holding organization data use row-level security (RLS) in Postgres: each transaction sets the organization with a transaction-scoped set_config and the policies filter by it. An integration test covers isolation between organizations.

Access tokens last 15 minutes and refresh tokens 30 days by default. After 5 failed attempts the account is locked for 15 minutes, and login also has a limit of 10 attempts per 15-minute window (in Redis when available, in memory otherwise). For nonexistent accounts the same password hash is computed, so response time does not reveal whether the user exists.

Untrusted content and the code sandbox

Everything that comes from outside (emails, API responses, files) goes through a deterministic pipeline before reaching the model: text is normalized (NFKC, invisible characters removed), credentials, one-time codes and card numbers are masked, markdown images and links are neutralized, the text is truncated, scored with injection heuristics and wrapped in a delimited block as data. A high score flags the task and raises approval for its actions. The score is a signal, not a barrier; the barrier is permissions, approvals and limits.

Code an agent wants to run is a high-risk request: it is shown in full to a person, and only after approval does the backend send it to the runner. The container has no network, a read-only root filesystem, an unprivileged user, all capabilities dropped, CPU, memory and process limits, a hard timeout, output caps and an extension allow-list. It receives none of the runner's environment variables and no access to the drive or the backend. Changing the code or an input requires a new approval, and the kill switch aborts a run in progress.

What is not covered

There are no certifications (neither SOC 2 nor ISO) and the project is not ready for regulated enterprise environments. There is no single sign-on (SSO). Audit export is a plain JSONL or CSV dump, with no signature and no external anchoring of the chain head.

Known limits: recovery after a restart assumes a single instance; with several replicas, semaphores and several counters are per process or last-writer-wins. A call already sent to the runtime finishes even if the kill switch is activated. Some state lives in process memory. The finer permission approvals:decide:high does not exist: deciding today equals being admin or owner. The forbid_self_approval option ships disabled for compatibility with one-person teams.

The code sandbox mounts the Docker socket in the runner, which is equivalent to root access on the host. For anything beyond a single trusted host, use a dedicated rootless or remote daemon and a runtime such as gVisor. Out of scope for now: per-organization model keys stored in the vault, undoing actions, and unified spending caps per connection or tool.

Tip. If you are evaluating the project for production, treat this page as the starting point of your own review, not as a guarantee.
