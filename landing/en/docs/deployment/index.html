Production deployment

AI Workforce OS is deployed with a standalone production compose file: Caddy terminates TLS and routes to the frontend (Next.js) and the backend (Go); the backend talks to the agent runtime (Python), Postgres and Redis. This guide covers installation, operation and the reduced layout used for a single-host demo.

Topology

docker-compose.prod.yml is standalone: it is not combined with the development docker-compose.yml. It uses a single domain. Caddy sends /api/* and /ws to the backend (internal port 8080) and everything else to the frontend (internal port 3000).

Only Caddy publishes ports (80, 443 TCP and 443 UDP). Postgres, Redis, the runtime, the backend and the frontend live on the internal network, declared with internal: true and therefore with no internet access. The runtime also joins the egress network so it can call model provider APIs. Caddy uses the edge network plus internal.

The frontend is built with relative paths (/api/v1) and derives the WebSocket URL from window.location (wss:// under HTTPS), so a single-domain deployment does not need baked NEXT_PUBLIC_* variables.

Requirements

  1. A Linux server with Docker Engine and the Docker Compose v2 plugin, with ports 80 and 443 open in the firewall.
  2. A domain with an A record (and AAAA if you have IPv6) pointing to the server. Let's Encrypt fails if DNS does not resolve yet.
  3. Access to the images on GHCR. If the packages are private, run docker login ghcr.io with a token that has read:packages. Alternative: build locally with --build.
  4. At least one model provider credential for the runtime (see the configuration page).

Step-by-step installation

The commands use example.com as the domain and OWNER and TAG as placeholders. All state lives in named volumes; the .env.prod file stays out of git (the repository .gitignore already ignores .env.*).

git clone <repo-url> && cd <repo>
cp .env.prod.example .env.prod
chmod 600 .env.prod

# Edit: DOMAIN, ACME_EMAIL, ALLOWED_ORIGINS, OWNER, TAG, provider keys...
$EDITOR .env.prod
Tip. If passwords contain special characters, DATABASE_URL and REDIS_URL break because they embed the passwords in the URL. Use hex secrets or percent-encode them.

Generating secrets and validating the configuration

Generate a different value for POSTGRES_PASSWORD, REDIS_PASSWORD and JWT_SECRET. The backend requires JWT_SECRET to be at least 32 bytes when authentication is on. The production compose sets AUTH_ENABLED to true. Defining RUNTIME_TOKEN is also recommended: a secret shared between backend and runtime (the backend warns when it is empty).

Variables marked as required in the compose file (DOMAIN, ACME_EMAIL, POSTGRES_PASSWORD, REDIS_PASSWORD, OWNER, TAG, JWT_SECRET, ALLOWED_ORIGINS, DEEPSEEK_API_KEY) make the validation command fail when missing.

openssl rand -hex 32   # repeat for POSTGRES_PASSWORD, REDIS_PASSWORD, JWT_SECRET and RUNTIME_TOKEN

# Validate before starting (fails if a required variable is missing)
docker compose -f docker-compose.prod.yml --env-file .env.prod config -q

Starting and checking health

Every service defines a healthcheck and dependencies use condition: service_healthy, so the start order is Postgres and Redis, runtime, backend, and finally frontend and Caddy. The backend exposes /healthz and so does the runtime. Caddy obtains and renews the certificate automatically.

C="docker compose -f docker-compose.prod.yml --env-file .env.prod"

$C pull          # option A: images published by CI
# $C build       # option B: build locally
$C up -d
$C ps            # every service should become healthy
curl -fsS https://example.com/ -o /dev/null && echo OK
$C logs -f backend

Updating, migrations and rollback

To update, change TAG to a sha-<short> value published by CI and bring the stack up again. Always take a pg_dump before deploying a version that carries migrations.

The backend applies embedded SQL migrations at startup, forward-only (schema_migrations table, no down migrations). If the new version fails and the schema has already changed, there are two paths: restore the previous dump and go back to the old TAG (data written afterwards is lost), or ship a new corrective migration, which is preferable once new data exists. If the migration only added columns or tables, the previous TAG usually keeps working without touching the database.

# 1) backup (see Backups)
# 2) point to the new tag
sed -i 's/^TAG=.*/TAG=sha-<NEW>/' .env.prod
$C pull
$C up -d

# Rollback without schema changes: restore the previous TAG
sed -i 's/^TAG=.*/TAG=sha-<PREVIOUS>/' .env.prod
$C pull && $C up -d

# Applied migrations
$C exec postgres psql -U workforce -d workforce -c 'select * from schema_migrations order by applied_at'

Postgres backups and restore

Postgres is the system of record. Redis keeps an AOF in the redisdata volume and should be treated as a cache and queue. Schedule pg_dump with cron, copy the files off the server and test a restore at least once.

mkdir -p backups
$C exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > backups/workforce-$(date +%F-%H%M).dump

# Restore
$C stop backend
$C exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" --if-exists "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
$C exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < backups/FILE.dump
$C start backend
Tip. docker compose down keeps the volumes. Do not use -v unless you want to delete the data.

Go-live checklist

  1. DNS points to the server, 80 and 443 are open and docker compose ps only shows published ports on caddy.
  2. .env.prod has 600 permissions and is outside git.
  3. JWT_SECRET, POSTGRES_PASSWORD and REDIS_PASSWORD are unique and random (32 bytes hex or more).
  4. ALLOWED_ORIGINS is exactly https://example.com; AUTH_ENABLED is true; ENABLE_DEMO_RESET is false; SIMULATION is false.
  5. At least one valid model provider is set, ALLOWED_PROVIDERS reflects the company data policy and BUDGET_USD is defined.
  6. TAG points to a specific sha-<short> (not latest) that passed CI.
  7. All services are healthy, login works and the WebSocket connects at wss://example.com/ws.
  8. The Postgres backup is scheduled and a restore has been tested.
  9. Logs rotate (json-file, 10 MB times 5 files, already configured) and memory and CPU limits fit the host.
Tip. The current compose only passes DEEPSEEK_API_KEY, ANTHROPIC_API_KEY, MODEL, RUNTIME_TOKEN and ALLOWED_PROVIDERS to the runtime, and DEEPSEEK_API_KEY is required. To use a custom endpoint or other runtime variables, add them to the agent-runtime service in the compose file.

Image publishing in CI

The .github/workflows/ci.yml workflow builds and tests backend, runtime and frontend, runs govulncheck and npm audit (non-blocking), hadolint, a smoke test and Playwright E2E. On a push to main, the publish job pushes the three images (aiworkforce-backend, aiworkforce-agent-runtime, aiworkforce-frontend) to GHCR with the tags sha-<short> and latest, using GITHUB_TOKEN with packages: write.

In the repository you must allow GITHUB_TOKEN to write packages and, after the first publish, link the packages to the repository and adjust their visibility. The repository variables NEXT_PUBLIC_API_URL and NEXT_PUBLIC_WS_URL must stay undefined for a single-domain deployment.

Reduced single-host layout

The deploy/vps directory holds the layout used for a public demo on a shared server that already runs its own Caddy owning ports 80 and 443. There the compose publishes no ports: the edge services (backend, frontend and the static landing) join the existing Caddy network under unique aliases, and everything else stays on a private network.

This is a demo setup, not a production one: the runtime runs in SIMULATION mode (no keys, no cost), there is no Postgres or Redis (in-memory storage), AUTH_ENABLED is false and ENABLE_DEMO_RESET is true. The frontend is built with absolute NEXT_PUBLIC_API_URL and NEXT_PUBLIC_WS_URL, and the app site adds X-Robots-Tag noindex. Routes /api/* and /ws go to the backend and the rest to the frontend, as in the production Caddyfile. The deploy.sh script does pull, a low-priority build and up -d --wait.

example.com        -> landing (static)
app.example.com    -> /api/* and /ws -> backend:8080 ; rest -> frontend:3000
(existing Caddy terminates TLS; this project publishes no ports)
