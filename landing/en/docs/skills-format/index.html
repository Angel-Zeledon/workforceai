Skills format

A skill is reusable know-how that an agent can load when it needs it. It uses the open Agent Skills format: a folder with a SKILL.md file and optional text resources. It is plain prompt text plus one gateway tool, so it works the same with every model provider.

What a skill package is

A package is a folder whose only required file is SKILL.md: a YAML frontmatter block followed by markdown instructions. It may include supporting files such as templates, examples, reference documents or scripts, always as text.

The files of each version are stored in the organization's drive, at /Shared/Skills/<name>/v<n>/, and the database keeps the manifest (path, size and sha256 of each file). Versions are immutable: restoring an old version creates a new one.

client-email/
├── SKILL.md
├── templates/
│   └── follow-up.md
└── examples/
    └── collection.txt

SKILL.md frontmatter

The parser understands only a small subset of YAML: scalars, quoted strings, blocks with > or |, inline or block lists and one level of nested map for metadata. It does not support anchors, tags, merges or code, and it rejects tabs in indentation.

SKILL.md must be valid UTF-8, start with a --- line and close the block with another. The instructions after the frontmatter cannot be empty.

FieldRequiredRule or limit
nameYesPattern ^[a-z0-9-]{1,64}$. Unique per organization and immutable.
descriptionYesUp to 1024 characters. It is what the agent sees to decide whether to use the skill.
licenseNoFree text.
compatibilityNoFree text; preserved on export.
allowed-toolsNoUp to 20 entries. Informational: it never grants anything.
metadataNoKey-to-text map, up to 30 entries (for example category).
Tip. Other top-level scalar keys are preserved on import and export, so a round trip does not lose data.

Complete annotated example

This is the client-email starter package in English, as shipped with the backend. The limits from the previous section hold: the name uses lowercase and hyphens, the description is short, and metadata carries the category and the built-in marker.

---
name: client-email
description: "Write a clear email to a client: subject, brief context, a concrete request or answer and the next step. Use it for replies, follow-ups, friendly collections and announcements."
metadata:
  category: communication
  builtin: "true"
---

# Client email

## When to use it
To write replies, follow-ups or notices to clients.

## Steps
1. Identify the goal in one sentence: inform, ask, confirm, collect or apologize.
2. Specific subject (at most 8 words) with the topic and, if relevant, the date or reference.
3. First paragraph: the answer or request. Then the minimum context.
4. Close with a single next step, who does it and by when.
5. Adjust the tone: warm and professional; in complaints acknowledge the problem first; in collections be firm and kind.

## Quality criteria
- Under 150 words unless more is needed.
- No figure, date or commitment that is not in the task data.
- Check names, amounts and attachments mentioned.

## Limits
Leave the email as a draft; sending it is decided by a person or by the organization policy.

Package limits

These caps are validated on create, edit and import. A violation returns a stable error code, for example file_too_large, too_many_files or zip_bomb.

Built-in starter skills

The backend ships a catalog of starter skills as data embedded in the binary, in Spanish and English and in the same format as an import, under builtin/<language>/<name>/ (currently 55 per language, including bank-reconciliation, b2b-proposal, service-contract-review, month-end-close, client-email and project-plan).

The first time an organization uses the library they are created as active, in the organization's language. If the organization already has any skill, even a deleted one, it is left as is, and deleted starters are not re-created. Role templates declare default_skills (names only) and agents of that role receive them without needing an assignment.

backend/internal/skills/builtin/
├── es/<nombre>/SKILL.md
└── en/<nombre>/SKILL.md

Lifecycle and statuses

A skill is in one of four statuses: draft, in_review, active or disabled. Holders of the skills:write permission (members) create drafts, edit and import. Only holders of skills:review (administrators) review, activate, disable and delete. A review names the version the reviewer read (otherwise stale_review) and re-verifies the file hashes before activating.

An import always enters in_review. If a member edits an active skill, the new version lands in in_review and agents keep using the approved version; if an administrator edits it, the edit is the review and it becomes active. A rejection returns to draft (or leaves the previous approved version active) with a note. Deletion is soft: creating another skill with the same name brings it back with a new version.

create (member)  → draft ──submit──▶ in_review ──approve (admin)──▶ active
import (member)  → in_review (always)
reject → draft, or stays active with the previous approved version
disable / approve again · delete (soft)

Scanning, import and export

When each version is saved, the package is scanned and warnings are stored for the reviewer: injection (a file's injection score exceeds the threshold), script (files that are executable as text), allowed_tools (allowed-tools was declared) and import_note. The scan informs; it does not decide on its own. The reviewer sees everything before approving.

A .zip or a single SKILL.md can be imported. Validation is strict: paths with .. or absolute ones, backslashes, drive letters, symlinks and special files, encrypted entries, case-insensitive duplicates and zip bombs are rejected. A single wrapper folder is stripped and __MACOSX and .DS_Store are ignored. Import from a URL is deliberately not implemented, because it would need an SSRF-safe fetcher.

Export returns a deterministic zip in the standard layout (<name>/SKILL.md plus resources, no executable bits) or only SKILL.md. Importing an export again gives the same instructions, description, metadata and files.

POST /skills/import           # .zip or SKILL.md
GET  /skills/{id}/export      # deterministic zip
POST /skills/{id}/submit      # draft → in_review
POST /skills/{id}/review      # approve or reject (skills:review)

Assignment to agents

Assignment links a skill to an agent (skill_assignments table) through PUT and DELETE on /agents/{id}/skills/{skillId}, with the agents write permission. There are also role defaults: names in a role template's default_skills reach every agent of that role without an assignment row.

A skill is served to an agent only if it is assigned (or is a default of its role) and its approved version is active and enabled. In any other situation the load is denied with skill_not_available.

How skills reach the model

Progressive disclosure in two steps. On every run, the backend adds to the request only the name and description of the agent's servable skills, with caps: at most 12 skills, 240 characters per description and 3000 characters in total. The runtime renders them as prompt lines with the rule that a skill guides how to work and never grants tools, connections, permissions, autonomy or approvals.

If a skill applies, the agent asks for it with a tool request. The Tool Gateway serves it as a native read tool (subject to the kill switch, pause and audit) and answers with the approved version's body without frontmatter plus the file list; with file it returns one specific resource.

The text travels in its own channel (loaded_skills) as trusted organization configuration, inside dedicated delimiters and not as untrusted data, because a person approved that exact version. It is still cleaned (invisible characters, credentials, forged delimiters), bounded (24,000 characters per answer, 4 loaded skills per task) and scored for injection. Scripts are inert text: running them requires the code tool with human approval.

{ "tool": "skill", "action": "load", "args": { "name": "client-email", "file": "templates/follow-up.md" } }
