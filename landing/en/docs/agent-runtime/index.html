Agent runtime

The agent runtime is a Python service (FastAPI and CrewAI) that turns a task and its context into a structured result. It talks only to model providers. Everything with side effects, such as tools, credentials, approvals and running code, stays in the Go backend.

Role and HTTP contract

The backend calls the runtime over HTTP with a task, the agent profile and the context it assembled. The runtime returns validated structured output and, if the agent wants to act, a list of tool_requests. It never executes a tool and never calls an external system. This keeps the trust boundary in one place: the model may be misled by untrusted text, but it can only propose.

When RUNTIME_TOKEN is set in both services, the runtime requires an Authorization bearer header on every route except /healthz, compared in constant time. It is optional so existing deployments do not break; set it in production. The main endpoints are:

EndpointPurpose
POST /v1/plan, /v1/plan-phases, /v1/plan-phase, /v1/replanTurn a request into a plan of tasks for the available agents
POST /v1/run-taskRun one task for one agent; returns structured output and optional tool_requests
POST /v1/consult, /v1/review, /v1/synthesize, /v1/summarizeAgent-to-agent questions, review, final report, summaries
POST /v1/route, /v1/chat-replyChat routing and conversational replies
POST /v1/estimateCost range before running; does not call the model
POST /v1/provider-testOne small real call to test an organization's key
GET /healthzStatus, mode (simulation or live), configured and default provider; never keys

Simulation and live mode

SIMULATION=true selects a scripted engine. It returns plausible plans, results, token counts and costs with simulated latency (SIM_LATENCY_SCALE=0 removes the delay). It needs no keys, makes no network calls and costs nothing. It also ignores the provider policy because no data leaves the process. The same engine is used when no provider is configured at all, and /healthz then reports mode simulation.

In live mode a CrewAI engine runs one agent, task and crew per role, with output validated against a StructuredOutput schema. Fields that exist only in live mode (provider, model, usage.failed_providers) are omitted in simulation, so the contract does not change. SIMULATION=true always wins, including over an organization's own key.

Model providers

Three providers are supported and at least one must be configured: deepseek, anthropic and custom, an OpenAI-compatible endpoint that can be regional, a local vLLM or Ollama, or your own gateway. A custom model is passed as openai/<name>. A model that costs nothing, such as a local one, can be priced at 0 with the custom price variables.

Organizations can also bring their own key. It is sealed with the organization's data key (AES-256-GCM, wrapped by CONNECTIONS_KEK), is never returned by any endpoint beyond its last four characters, and travels in clear only on the internal, token-authenticated hop from the backend to the runtime.

ProviderConfigurationNotes
deepseekDEEPSEEK_API_KEY, DEEPSEEK_MODELThird-party API; default model deepseek/deepseek-chat
anthropicANTHROPIC_API_KEY, ANTHROPIC_MODELThird-party API; see the runtime README for the default model
customCUSTOM_LLM_BASE_URL (required), CUSTOM_LLM_API_KEY, CUSTOM_LLM_MODELAny OpenAI-compatible endpoint: regional, vLLM or Ollama, own gateway. Prices via CUSTOM_PRICE_IN_PER_M and CUSTOM_PRICE_OUT_PER_M

Provider order and fallback

For each call the runtime builds an attempt list from three sources, each adding only the providers not yet listed: MODEL_PROVIDER_ORDER_<ROLE> (the agent role in capitals, or PLAN, CONSULT, SYNTHESIZE), then the request's preferred_providers, then the global MODEL_PROVIDER_ORDER (default deepseek, anthropic, custom). Every configured and permitted provider is therefore a fallback.

A transient failure (timeout, rate limit, 5xx) is retried on the same provider PROVIDER_RETRIES times (default 1, with PROVIDER_RETRY_BACKOFF_S) before moving to the next. PROVIDER_TIMEOUT_S bounds each attempt. The response reports which provider and model answered and which ones failed first. Per-role models can be overridden by the organization policy, but only for a provider that is already configured and allowed.

# Runtime (agent-runtime)
SIMULATION=false                 # true: scripted engine, no network, no cost
DEEPSEEK_API_KEY=...             # at least one provider is enough
ANTHROPIC_API_KEY=...
CUSTOM_LLM_BASE_URL=https://llm.internal.example/v1   # OpenAI-compatible
MODEL_PROVIDER_ORDER=anthropic,deepseek,custom
MODEL_PROVIDER_ORDER_LEGAL=anthropic                  # per role / task
ALLOWED_PROVIDERS=anthropic,custom                    # operator ceiling
RUNTIME_TOKEN=<shared secret>    # same value in the backend

# Backend
RUNTIME_URL=http://runtime:8000
BUDGET_USD=50                    # organization budget
REQUEST_BUDGET_CAP_USD=...       # per-request cap
AGENT_BUDGET_USD=...             # per-agent cap

Data policy: ALLOWED_PROVIDERS

The data policy is applied before anything is sent. The effective list is the operator's ALLOWED_PROVIDERS intersected with the allowed_providers in the request. A provider outside the list is neither called nor used as a fallback, and a request can narrow the operator ceiling but never widen it.

The backend fills allowed_providers from each organization's model policy (owner and admin can edit it, and every change is audited). If the intersection is empty it sends a sentinel value that no provider matches, so the runtime refuses the call instead of widening the set. Failures are explicit, never silent:

{
  "detail": {
    "code": "no_allowed_provider",
    "message": "...",
    "providers_tried": [],
    "allowed_providers": ["anthropic"],
    "configured_providers": ["deepseek"]
  }
}
Tip. no_allowed_provider returns HTTP 422 and nothing is sent. all_providers_failed returns HTTP 502 and lists providers_tried.

What leaves the process and redaction

Only the prompts of each call reach a provider: the user's request text, the agent's persona, responsibilities and tool list, outputs of dependency tasks, agent memory, external content, tool results that the backend already filtered, and consult or synthesis questions. Credentials, connection ids, API URLs and tokens are not part of the contract, so they cannot be sent.

Secrets are redacted twice. The backend redacts tool results first; the runtime's redact module is the second barrier and covers private keys, JWTs, GitHub, AWS and Google tokens, API keys, bearer tokens, password-style assignments, URLs carrying tokens and Luhn-valid card numbers. It applies to prompt input and to model output, and provider error messages pass through it too. External content, dependency outputs and memory are inserted only in the user prompt, inside blocks marked as untrusted data with an instruction not to obey them. The system prompt is built only from backend-supplied persona, responsibilities and tools.

Tools: the model asks, the backend executes

A tool request is a proposal. The backend checks the agent's tool list, the argument schema, constraints such as allowed domains, the policy engine and the autonomy level, and may create an approval for a person. Only then does the tool gateway run the tool, using credentials from the encrypted vault that never leave the backend. The result is returned to the model redacted and delimited as untrusted data.

Actions with irreversible external effects, such as sending an email, always require a human decision, regardless of the agent's autonomy. An approved action is claimed at most once, so a restart cannot run it twice. Tools without a connection use in-memory fake adapters, which is how simulation works end to end.

{
  "tool_requests": [
    { "tool": "email", "action": "send",
      "args": { "to": "customer@example.com", "subject": "Proposal" } }
  ]
}

Code sandbox

The code tool, action run, lets an agent ask to execute Python. It is off by default and every run becomes a high-risk approval showing the full code, input files, purpose and limits; nothing can skip that step. The approval is bound to a hash of the code and the SHA-256 of every input, so changing either requires a new approval.

After approval the backend sends the run to a separate runner that starts a disposable container with no network, a read-only root, a non-root user, all capabilities dropped, CPU, memory and process limits, a timeout, output caps and an allow-list of output file types. The runner's environment is not forwarded, so no secrets reach the code. Kill switch, pause or read-only mode abort a running job. It needs SANDBOX_URL and SANDBOX_TOKEN in the backend; the runner mounts the Docker socket, which is root-equivalent on that host.

Cost accounting and budgets

Prices live in one table, model_prices.json, in USD per million tokens, embedded in the backend and copied byte for byte into the runtime; a test in each service enforces that they match. A model missing from the table is billed at a conservative default and logged once. PRICE_IN_PER_M and PRICE_OUT_PER_M force a rate for every provider, and the table is not a statement of what your own provider contract charges.

Before each model call the backend reserves the maximum estimate against the request, the agent and the organization, then records the greater of the runtime's reported cost and its own recalculation, so it does not depend on the runtime's accuracy. Spending is read from a ledger in Postgres. /v1/estimate gives a range before running, never a single figure. Limits:
