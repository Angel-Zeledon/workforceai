Security at AI Workforce OS

This page summarizes the security controls that are implemented today, as can be checked in the code and in the deployment configuration, and ends with a table of what we do not have yet. We hold no certifications (neither SOC 2 nor ISO 27001) and we do not claim compliance with any framework. If your procurement team needs more detail, write to info@workforceai.es.

How to read this page

We describe only what exists. When something depends on configuration (for example e-mail verification or the vault encryption key) we say so explicitly. The current public deployment shares a single server and, according to its configuration in the repository, the agent runtime runs in simulation mode: it sends no data to any model provider until a real AI key is configured.

The design starts from the premise that a language model can be fooled by untrusted text. That is why damage is limited with deterministic controls in the backend (Go) and not with instructions in the prompt. We do not promise that the model is never influenced; we promise that the blast radius is bounded to what the backend authorizes.

Tip. More technical detail in the documentation: security model and authentication and multi-organization.

Isolation between organizations

Tables holding organization data use Postgres row-level security. Each request runs in a transaction that sets the organization with a transaction-local setting, and policies filter on it; FORCE ROW LEVEL SECURITY applies it even to the table owner.

The system fails closed: if the organization is not set, no row is visible or writable. The server connects with a role that is not a superuser, has no BYPASSRLS and owns no tables. An integration test covers isolation between organizations. This is logical isolation inside one database, not separate instances per customer.

Authentication and sessions

Passwords are stored with Argon2id (64 MiB, 3 iterations, 2 lanes by default) and are rehashed at the next login if they were created with weaker parameters. Passwords must be 10 to 128 characters long, use at least two character classes, and common passwords are rejected.

After 5 wrong passwords the account is locked for 15 minutes. There are rate limits per e-mail and per IP (for example 10 login attempts per 15 minutes per e-mail, 20 per IP, and 5 sign-ups per hour per IP), kept in Redis when available or in memory otherwise. For non-existent accounts an equivalent hash is computed so that response time does not reveal whether an e-mail exists.

The access token is a JWT valid 15 minutes by default. The refresh token is opaque, lasts 30 days by default, is stored on the server only as a SHA-256 hash and travels in an HttpOnly, SameSite=Strict cookie. Every refresh rotates the token within a family; presenting an already-used token revokes the whole family. Refresh and logout require a dedicated anti-CSRF header.

E-mail verification with a single-use link (valid 24 hours) exists but is optional: it is turned on with EMAIL_VERIFICATION=true and requires a configured SMTP server. Trial accounts are disposable and stop working after 24 hours.

Roles and permissions

Each membership has one of four roles: owner, admin, member or viewer, and each is a strict superset of the one below. Permissions have the form resource:action and are checked on the server before each operation. By default the role is read from the database on every request, so demoting or removing a member takes effect immediately.

Nobody can assign a role higher than their own, the last owner cannot be removed and an agent never holds approval permissions. A user can belong to several organizations with a different role in each.

Credential vault

Integration credentials (OAuth tokens, API keys) are encrypted with AES-256-GCM in an envelope scheme: a key-encryption key (KEK) kept outside the database wraps a per-organization data key, and that key encrypts each secret with a random nonce. The authenticated data includes organization, credential, version and kind, so a ciphertext copied to another row or organization does not decrypt.

Without a configured KEK (CONNECTIONS_KEK) the vault fails closed: it neither stores nor reads real credentials. Several KEKs are accepted so they can be rotated. Revoking a connection suspends it, calls the provider's revocation endpoint and destroys the ciphertext. The language model never sees a secret: the contract between backend and runtime has no credential fields.

An organization's own AI keys (bring your own key) are stored with the same envelope encryption.

Human approvals

An agent can request an action but can never approve it. People with the admin or owner role approve; the role comes from the session token. Each approval is bound by hash to the exact arguments, is consumed once, is re-validated before execution and expires (48 hours by default; expiring counts as a rejection).

There are four autonomy levels per agent (suggest, approve_each, rules, autonomous); the default level requires approval for any action with an external effect. An organization can add rules such as amount thresholds, forbidden actions, new recipients or dual approval, in which two distinct people are needed and the requester never approves.

Known limitation: there is no finer-grained permission for deciding high-risk approvals today; deciding equals being admin or owner. The option that prevents self-approval ships turned off for compatibility with one-person teams.

Spending caps and operating controls

Before each runtime call the maximum estimated cost is reserved against the request, the agent and the organization, and afterwards it is reconciled with the larger of the cost reported by the runtime and the cost recomputed by the backend. When a cap is reached the request or agent pauses and a person decides whether to raise it. There are also anti-loop limits: delegation depth, tasks per request, retries, time per task and a per-organization queue.

Operating hours are a weekly schedule with a time zone that prevents starting new work outside open hours. Anomaly detection v1 applies four explainable rules (spend spike, burst of tool requests, serial rejected approvals and new recipient domains) and records each finding in the audit log; on its own it does not block, and automatic freezing is optional and off by default.

Read-only mode (organization-wide or per agent) denies external effects. The kill switch has two levels, freeze and lockdown: any admin or owner can trigger it, only an owner can lift it and with a written reason; it can also be imposed through an environment variable. Held actions go back to the approval queue and must be approved again. A call already sent to the runtime finishes even if the kill switch is triggered.

Verifiable audit log

The audit log is a hash chain per organization: each entry includes the SHA-256 of the previous one, so modifying, deleting, reordering or inserting an entry breaks the chain from that point on. A verification endpoint recomputes the chain and an export endpoint returns the log as JSONL or CSV (admin or owner permission). For the application role the log is append-only: UPDATE and DELETE are revoked.

Before being chained, each entry goes through a scrubber that keeps only metadata: it replaces content fields and credential-looking keys with [redacted], masks embedded secrets and truncates long texts. Authentication, policy decisions, approvals, tool executions and control changes are audited, among others.

The export is a plain dump, with no external signature or anchoring of the chain head. Today there is no automatic purge of the audit log.

Data to AI models and untrusted content

Before text reaches the model, the runtime and the backend mask credentials, one-time codes and card numbers, and all external content (e-mails, API responses, files) is normalized, markdown images and links are neutralized and it is wrapped in a block delimited as data. A heuristic injection score flags the task and raises its approval; it is a signal, not a barrier. The barrier is permissions, approvals and limits.

Each organization can set an allow-list of AI providers, on top of the ceiling defined by the deployment operator (ALLOWED_PROVIDERS). An excluded provider is neither called nor used as a fallback. Organizations can bring their own AI key and require that only that key is used (no fallback to the platform's keys), or point to their own OpenAI-compatible endpoint. The providers the system recognizes are deepseek, anthropic, openai, kimi and custom. Details on the subprocessors page.

Code that an agent wants to run is a high-risk request that a person must approve. It runs in a container with no network, a read-only file system, no capabilities and resource limits. Known limitation: the executor mounts the Docker socket, which is equivalent to administrator access to the host; we do not recommend it beyond a single trusted host.

Encryption in transit, backups and development

Public traffic arrives over HTTPS: a Caddy proxy terminates TLS with automatic certificates and sends the Strict-Transport-Security header (one year) on the site and the application. The application also adds X-Content-Type-Options, X-Frame-Options DENY and Referrer-Policy. We have not had the TLS configuration externally assessed. Between containers, on a private network of the same server, the connection to Postgres does not use TLS (sslmode=disable). We have not verified encryption at rest of the hosting provider's disks.

Backups: a cron job runs once a day (03:30, server time) a gzip-compressed Postgres dump. It is stored on the same server with restrictive permissions, kept for 14 days, and the script fails with a message if the file is suspiciously small. One restore has been tested. There is no off-server copy and no formal recovery time or recovery point objective.

Development: the repository runs in CI the build, tests, a race detector on key packages, a Dockerfile linter, govulncheck and npm audit (the last two do not block integration). Deployments use images tagged by commit.
