Arquitectura de AI Workforce OS

AI Workforce OS separa la decisión de la ejecución: un backend en Go es la fuente de verdad, un runtime en Python solo razona con el LLM y un frontend en Next.js dibuja la oficina a partir de eventos. Esta página describe cómo encajan las piezas y cómo viaja una petición de punta a punta.

Componentes

El sistema son cinco procesos más un proxy opcional. Todo el estado de negocio vive en el backend; el runtime no guarda estado entre llamadas.

ComponenteTecnologíaResponsabilidad
FrontendNext.js, React Three FiberOficina 3D y modo dashboard. Consume REST y el WebSocket; toda animación deriva de eventos reales.
BackendGo, chiAPI REST /api/v1, WebSocket /ws, orquestador, aprobaciones, auditoría, presupuesto, autenticación y RBAC.
Agent runtimePython, FastAPIRecibe tarea y contexto, llama al proveedor LLM y devuelve resultado estructurado. Motor intercambiable.
PostgresPostgreSQLDatos de todas las organizaciones, con row-level security. Migraciones SQL numeradas.

CaddyCaddyProxy de producción: TLS automático, envía /api/* y /ws al backend y el resto al frontend.

Fronteras entre backend y runtime

La regla central: el runtime nunca habla con Postgres, Redis ni sistemas externos. Recibe una tarea con su contexto y devuelve un resultado, solicitudes de herramientas y consumo; solo contacta al proveedor del LLM. El backend decide permisos, autonomía y presupuesto, y ejecuta las herramientas.

El backend llama al runtime por HTTP con JSON. Si se define RUNTIME_TOKEN en ambos lados, las llamadas llevan ese secreto compartido. El motor de IA queda detrás de una interfaz propia, de modo que CrewAI puede reemplazarse sin tocar el backend.

Flujo de una petición

Una petición recorre este camino: la solicitud del usuario llega al orquestador, que pide un plan al runtime, lo valida y crea tareas; cada tarea se asigna a un agente que usa herramientas, las acciones sensibles esperan aprobación humana y al final se sintetiza un reporte.

  1. El usuario envía el texto con POST /api/v1/requests (o por el chat, que lo enruta). El backend responde 202 con request_id y emite request.received.
  2. El orquestador pide el plan al runtime. El backend valida agentes existentes, dependencias y límites antes de aceptarlo y emite plan.created y task.created.
  3. Las tareas se ejecutan respetando depends_on. Cada una cambia el estado del agente (agent.state_changed) y puede generar consultas entre agentes (message.sent) y una revisión de calidad (task.reviewed).
  4. Las herramientas que pide el runtime pasan por la política de autonomía y los permisos. Si hace falta aprobación se crea un registro pendiente y la tarea queda en awaiting_approval.
  5. Un usuario con permiso decide con POST /api/v1/approvals/{id}/decision. La tarea continúa o se bloquea.
  6. Cuando todas las tareas terminan, el runtime sintetiza el reporte; el backend emite report.created y request.completed.
  7. En paralelo se registra el costo por petición y se aplica el presupuesto: budget.warning y budget.exceeded pueden pausar la ejecución.
POST /api/v1/requests {"text": "..."}      -> 202 {"request_id": "..."}
  orchestrator -> runtime POST /v1/plan          -> tasks + depends_on
  backend validates the plan                     -> plan.created, task.created*
  per task: runtime POST /v1/run-task            -> output, consults, tool_requests, usage
  tool_requests -> policy/autonomy check         -> approval.requested (if needed)
  POST /api/v1/approvals/{id}/decision           -> approval.resolved, task resumes
  runtime POST /v1/synthesize                    -> report.created, request.completed

Canal en tiempo real

GET /ws abre un WebSocket por organización. El backend publica cada evento en Redis (canal aiworkforce:events) y un hub reenvía el cuadro solo a los clientes cuyo org_id coincide; un cuadro sin org_id se descarta. Sin REDIS_URL el hub recibe los eventos de forma local.

Al conectar llega un evento hello con la lista de agentes. Después llegan los eventos de dominio. El servidor envía ping cada 30 s, cierra si no hay pong en 60 s y descarta a los clientes lentos (cola de 256 cuadros). Con autenticación activa el socket se cierra con el código 4401 cuando expira el token, para que el cliente reconecte. No hay replay: tras reconectar, el cliente recarga el estado por REST.

Multi-tenencia

Cada cuenta crea su propia organización y el org_id viaja dentro del token de acceso; nunca se toma de la entrada del cliente. La capa HTTP lo coloca en el contexto de la petición y todas las consultas se filtran por él.

Como defensa en profundidad, Postgres aplica row-level security. Cada transacción fija app.org_id con set_config y las políticas usan esa función; si el valor falta, la consulta no devuelve filas (falla cerrado). La aplicación se conecta con un rol sin privilegios de propietario (DB_APP_ROLE, por defecto app_user, sin BYPASSRLS), y las migraciones usan una conexión aparte (MIGRATE_DATABASE_URL). El hub del WebSocket también filtra por organización.

Simulación frente a IA real

El contrato HTTP del runtime es el mismo en ambos modos; cambia el motor. En simulación (por defecto, sin clave o con SIMULATION=true) el runtime devuelve resultados guionados con latencias simuladas, sin red y sin costo. En modo live usa el proveedor configurado y GET /healthz del runtime informa mode: live y el proveedor.

Si hay un proveedor configurado pero el motor real no arranca, el runtime responde en simulación con status degraded y un aviso; no hay fallback silencioso. El backend refleja el modo en su propio /healthz como runtime_mode.

Consejo. SIMULATION=true siempre gana: no se hace ninguna llamada de red, incluso con claves presentes.

Despliegue y borde

docker-compose.yml levanta postgres, redis, almacenamiento de objetos, agent-runtime, backend y frontend; existen variantes de demo y producción. En producción Caddy termina TLS, agrega cabeceras de seguridad y enruta por ruta: /api/* y /ws al backend, todo lo demás al frontend. La ejecución de código de los agentes usa una imagen y un runner de sandbox separados.
