Arquitectura de AI Workforce OS

AI Workforce OS separa la decisión de la ejecución: un backend en Go es la fuente de verdad, un runtime en Python solo razona con el modelo y un frontend en Next.js dibuja la oficina a partir de eventos. Esta página es para quien despliega, extiende o audita el sistema: cómo encajan las piezas y cómo viaja una petición de punta a punta.

Componentes#

Todo el estado de negocio vive en el backend; el runtime no guarda estado entre llamadas. Postgres, Redis, el almacenamiento de objetos y el sandbox son opcionales en desarrollo y tienen un modo de reserva.

Fronteras entre backend y runtime#

La regla central: el runtime nunca habla con Postgres, Redis ni sistemas externos. Recibe una tarea con su contexto y devuelve un resultado, solicitudes de herramientas y consumo; solo contacta al proveedor del modelo. El backend decide permisos, autonomía y presupuesto, y es el único que ejecuta herramientas.

El backend llama al runtime por HTTP con JSON en RUNTIME_URL. Si RUNTIME_TOKEN está definido en ambos lados, cada llamada lleva ese secreto como token bearer. El motor de IA queda detrás de una interfaz propia (AgentEngine), de modo que CrewAI puede reemplazarse sin tocar el backend.

Flujo de una petición#

La solicitud del usuario llega al orquestador, que pide un plan al runtime, lo valida y crea tareas. Cada tarea la ejecuta un agente que puede pedir herramientas; las acciones sensibles esperan aprobación humana y al final se sintetiza un reporte.

  1. El usuario envía el texto con POST /api/v1/requests (o por el chat, que lo enruta). El backend responde 202 con request_id y emite request.received.
  2. El orquestador pide el plan al runtime y lo valida antes de aceptarlo: claves duplicadas, dependencias desconocidas o circulares y profundidad máxima. Luego emite plan.created y task.created.
  3. Las tareas se ejecutan respetando depends_on. Cada una cambia el estado del agente (agent.state_changed) y puede generar consultas entre agentes (message.sent) y una revisión de calidad (task.reviewed).
  4. Las herramientas que pide el runtime pasan por la política de autonomía y los permisos. Si hace falta aprobación, se crea un registro pendiente (approval.requested) y la tarea queda en awaiting_approval.
  5. Un usuario con permiso decide con POST /api/v1/approvals/{id}/decision. La tarea continúa o se bloquea.
  6. Cuando todas las tareas terminan, el runtime sintetiza el reporte y el backend emite report.created y request.completed.
  7. En paralelo se registra el costo de cada llamada y se aplica el presupuesto: budget.warning avisa y budget.exceeded pausa la ejecución.

Canal en tiempo real#

GET /ws abre un WebSocket por organización. El backend publica cada evento en Redis (canal aiworkforce:events) y un hub reenvía el cuadro solo a los clientes cuyo org_id coincide; un cuadro sin org_id se descarta. Un cuadro con audience llega solo a esos usuarios.

Al conectar llega un evento hello con la lista de agentes y después los eventos de dominio. El cliente debe recargar el estado por REST tras reconectar, porque no hay replay.

  • El servidor envía ping cada 30 s y cierra si no recibe pong en 60 s.
  • Un cliente lento, con 256 cuadros en cola, se desconecta.
  • Con autenticación activa, el socket se cierra con el código 4401 a los 15 minutos (la vida por defecto del token de acceso) para que el cliente reconecte con un token nuevo.

Multi-tenencia#

El org_id viaja dentro del token de acceso y nunca se toma de la entrada del cliente. La capa HTTP lo coloca en el contexto de la petición y todas las consultas se filtran por él. Un usuario puede pertenecer a varias organizaciones y cambia de una a otra abriendo una sesión nueva.

Como defensa en profundidad, Postgres aplica row-level security:

  • Cada transacción fija app.org_id con set_config(..., true), local a la transacción; las políticas comparan org_id con app_current_org().
  • Si el valor falta, la consulta no ve ni escribe filas: falla cerrado.
  • La aplicación hace SET ROLE a un rol sin privilegios de propietario (DB_APP_ROLE, por defecto app_user, sin BYPASSRLS); las migraciones usan MIGRATE_DATABASE_URL.
  • El hub del WebSocket también filtra por organización.

Simulación frente a IA real#

El contrato HTTP del runtime es el mismo en ambos modos; cambia el motor. En simulación (con SIMULATION=true o sin ningún proveedor configurado) el runtime devuelve resultados guionados con latencias simuladas, sin red y sin costo. En modo real usa los proveedores configurados y su GET /healthz informa mode: live y el proveedor.

Si hay un proveedor configurado pero el motor real no arranca, el runtime responde en simulación con status: degraded y un aviso; no hay fallback silencioso. El backend refleja el modo en su propio GET /healthz como runtime_mode.

Consejo

SIMULATION=true siempre gana: no se hace ninguna llamada de red, incluso con claves presentes.

Despliegue y borde#

Hay tres archivos de Compose:

  • docker-compose.yml: desarrollo con cuentas. Levanta postgres, redis, objects (almacenamiento S3), agent-runtime, backend y frontend; el sandbox runner está en el perfil sandbox.
  • docker-compose.demo.yml: se combina con el anterior para el modo demo abierto (AUTH_ENABLED=false).
  • docker-compose.prod.yml: producción. caddy, postgres, redis, agent-runtime, backend y frontend; solo Caddy publica puertos (80 y 443).

Nota

En producción Caddy termina TLS, agrega cabeceras de seguridad (HSTS, X-Content-Type-Options, X-Frame-Options, Referrer-Policy) y enruta por ruta: /api/* y /ws al backend, todo lo demás al frontend.

Estructura del repositorio#

El backend sigue capas: api depende de application, que depende de domain; infrastructure implementa los puertos.
