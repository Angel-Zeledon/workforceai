Runtime de agentes

El runtime de agentes es un servicio en Python (FastAPI y CrewAI) que convierte una tarea y su contexto en un resultado estructurado. Solo habla con proveedores de modelo. Todo lo que tiene efectos, como herramientas, credenciales, aprobaciones y ejecución de código, queda en el backend en Go.

Rol y contrato HTTP

El backend llama al runtime por HTTP con una tarea, el perfil del agente y el contexto que armó. El runtime devuelve una salida estructurada validada y, si el agente quiere actuar, una lista de tool_requests. Nunca ejecuta una herramienta ni llama a un sistema externo. Así la frontera de confianza queda en un solo lugar: el modelo puede ser engañado por texto no confiable, pero solo puede proponer.

Cuando RUNTIME_TOKEN está definido en ambos servicios, el runtime exige una cabecera Authorization bearer en todas las rutas salvo /healthz, comparada en tiempo constante. Es opcional para no romper despliegues existentes; defínelo en producción. Los endpoints principales son:

EndpointPropósito
POST /v1/plan, /v1/plan-phases, /v1/plan-phase, /v1/replanConvierten una solicitud en un plan de tareas para los agentes disponibles
POST /v1/run-taskEjecuta una tarea para un agente; devuelve salida estructurada y tool_requests opcionales
POST /v1/consult, /v1/review, /v1/synthesize, /v1/summarizeConsultas entre agentes, revisión, informe final, resúmenes
POST /v1/route, /v1/chat-replyEnrutamiento de chat y respuestas conversacionales
POST /v1/estimateRango de costo antes de ejecutar; no llama al modelo
POST /v1/provider-testUna llamada real pequeña para probar la clave de una organización
GET /healthzEstado, modo (simulation o live), proveedor configurado y por defecto; nunca claves

Simulación y modo real

SIMULATION=true selecciona un motor guionado. Devuelve planes, resultados, conteos de tokens y costos plausibles con latencia simulada (SIM_LATENCY_SCALE=0 elimina la espera). No necesita claves, no hace llamadas de red y no cuesta nada. También ignora la política de proveedores porque ningún dato sale del proceso. El mismo motor se usa cuando no hay ningún proveedor configurado, y entonces /healthz informa el modo simulation.

En modo real un motor CrewAI corre un agente, una tarea y un crew por rol, con la salida validada contra un esquema StructuredOutput. Los campos que solo existen en modo real (provider, model, usage.failed_providers) se omiten en simulación, así que el contrato no cambia. SIMULATION=true siempre gana, incluso sobre la clave propia de una organización.

Proveedores de modelo

Se admiten tres proveedores y se necesita al menos uno configurado: deepseek, anthropic y custom, un endpoint compatible con OpenAI que puede ser regional, un vLLM u Ollama local o tu propia pasarela. Un modelo custom se pasa como openai/<nombre>. Un modelo sin costo, como uno local, puede tarificarse en 0 con las variables de precio custom.

Las organizaciones también pueden traer su propia clave. Se sella con la clave de datos de la organización (AES-256-GCM, envuelta por CONNECTIONS_KEK), ningún endpoint la devuelve salvo sus últimos cuatro caracteres, y viaja en claro solo por el salto interno, autenticado con token, del backend al runtime.

ProveedorConfiguraciónNotas
deepseekDEEPSEEK_API_KEY, DEEPSEEK_MODELAPI de terceros; modelo por defecto deepseek/deepseek-chat
anthropicANTHROPIC_API_KEY, ANTHROPIC_MODELAPI de terceros; el modelo por defecto está en el README del runtime
customCUSTOM_LLM_BASE_URL (obligatoria), CUSTOM_LLM_API_KEY, CUSTOM_LLM_MODELCualquier endpoint compatible con OpenAI: regional, vLLM u Ollama, pasarela propia. Precios con CUSTOM_PRICE_IN_PER_M y CUSTOM_PRICE_OUT_PER_M

Orden de proveedores y respaldo

Para cada llamada el runtime arma una lista de intentos con tres fuentes, cada una agrega solo los proveedores que faltan: MODEL_PROVIDER_ORDER_<ROL> (el rol del agente en mayúsculas, o PLAN, CONSULT, SYNTHESIZE), luego preferred_providers de la solicitud y por último MODEL_PROVIDER_ORDER global (por defecto deepseek, anthropic, custom). Así, todo proveedor configurado y permitido es un respaldo.

Un fallo transitorio (timeout, límite de tasa, 5xx) se reintenta en el mismo proveedor PROVIDER_RETRIES veces (1 por defecto, con PROVIDER_RETRY_BACKOFF_S) antes de pasar al siguiente. PROVIDER_TIMEOUT_S acota cada intento. La respuesta indica qué proveedor y modelo contestaron y cuáles fallaron antes. La política de la organización puede cambiar el modelo por rol, pero solo de un proveedor ya configurado y permitido.

# Runtime (agent-runtime)
SIMULATION=false                 # true: scripted engine, no network, no cost
DEEPSEEK_API_KEY=...             # at least one provider is enough
ANTHROPIC_API_KEY=...
CUSTOM_LLM_BASE_URL=https://llm.internal.example/v1   # OpenAI-compatible
MODEL_PROVIDER_ORDER=anthropic,deepseek,custom
MODEL_PROVIDER_ORDER_LEGAL=anthropic                  # per role / task
ALLOWED_PROVIDERS=anthropic,custom                    # operator ceiling
RUNTIME_TOKEN=<shared secret>    # same value in the backend

# Backend
RUNTIME_URL=http://runtime:8000
BUDGET_USD=50                    # organization budget
REQUEST_BUDGET_CAP_USD=...       # per-request cap
AGENT_BUDGET_USD=...             # per-agent cap

Política de datos: ALLOWED_PROVIDERS

La política de datos se aplica antes de enviar nada. La lista efectiva es el ALLOWED_PROVIDERS del operador intersectado con el allowed_providers de la solicitud. Un proveedor fuera de la lista ni se llama ni se usa como respaldo, y una solicitud puede reducir el techo del operador pero nunca ampliarlo.

El backend completa allowed_providers desde la política de modelos de cada organización (owner y admin pueden editarla y cada cambio queda auditado). Si la intersección queda vacía envía un valor centinela que ningún proveedor cumple, así que el runtime rechaza la llamada en lugar de ampliar el conjunto. Los fallos son explícitos, nunca silenciosos:

{
  "detail": {
    "code": "no_allowed_provider",
    "message": "...",
    "providers_tried": [],
    "allowed_providers": ["anthropic"],
    "configured_providers": ["deepseek"]
  }
}
Consejo. no_allowed_provider devuelve HTTP 422 y no se envía nada. all_providers_failed devuelve HTTP 502 y lista providers_tried.

Qué sale del proceso y redacción

A un proveedor solo llegan los prompts de cada llamada: el texto de la solicitud del usuario, la persona, responsabilidades y herramientas del agente, salidas de tareas dependientes, memoria del agente, contenido externo, resultados de herramientas ya filtrados por el backend y preguntas de consulta o síntesis. Credenciales, connection_id, URLs de API y tokens no forman parte del contrato, así que no pueden enviarse.

Los secretos se redactan dos veces. El backend redacta primero los resultados de herramientas; el módulo redact del runtime es la segunda barrera y cubre claves privadas, JWT, tokens de GitHub, AWS y Google, claves de API, tokens bearer, asignaciones tipo password, URLs con tokens y números de tarjeta válidos por Luhn. Se aplica a la entrada del prompt y a la salida del modelo, y los mensajes de error de los proveedores también pasan por él. El contenido externo, las salidas de dependencias y la memoria se insertan solo en el prompt de usuario, dentro de bloques marcados como datos no confiables con la instrucción de no obedecerlos. El system prompt se arma solo con persona, responsabilidades y herramientas que da el backend.

Herramientas: el modelo pide, el backend ejecuta

Una solicitud de herramienta es una propuesta. El backend revisa la lista de herramientas del agente, el esquema de argumentos, restricciones como dominios permitidos, el motor de políticas y el nivel de autonomía, y puede crear una aprobación para una persona. Solo entonces el tool gateway ejecuta la herramienta, con credenciales de la bóveda cifrada que nunca salen del backend. El resultado vuelve al modelo redactado y delimitado como datos no confiables.

Las acciones con efectos externos irreversibles, como enviar un correo, siempre requieren una decisión humana, sea cual sea la autonomía del agente. Una acción aprobada se reclama como máximo una vez, así que un reinicio no puede ejecutarla dos veces. Las herramientas sin conexión usan adaptadores falsos en memoria, que es como funciona la simulación de punta a punta.

{
  "tool_requests": [
    { "tool": "email", "action": "send",
      "args": { "to": "customer@example.com", "subject": "Proposal" } }
  ]
}

Sandbox de código

La herramienta code, acción run, permite que un agente pida ejecutar Python. Está desactivada por defecto y cada ejecución se convierte en una aprobación de alto riesgo que muestra el código completo, los archivos de entrada, el propósito y los límites; nada puede saltarse ese paso. La aprobación queda ligada a un hash del código y al SHA-256 de cada entrada, así que cambiar cualquiera exige una aprobación nueva.

Tras la aprobación el backend envía la ejecución a un runner aparte que inicia un contenedor desechable sin red, con raíz de solo lectura, usuario no root, todas las capabilities eliminadas, límites de CPU, memoria y procesos, un timeout, topes de salida y una lista de tipos de archivo permitidos. El entorno del runner no se reenvía, así que ningún secreto llega al código. El kill switch, la pausa o el modo de solo lectura abortan una ejecución en curso. Requiere SANDBOX_URL y SANDBOX_TOKEN en el backend; el runner monta el socket de Docker, que equivale a root en ese host.

Contabilidad de costos y presupuestos

Los precios viven en una sola tabla, model_prices.json, en USD por millón de tokens, embebida en el backend y copiada byte a byte en el runtime; una prueba en cada servicio exige que coincidan. Un modelo ausente de la tabla se cobra a una tarifa por defecto conservadora y se avisa una vez en el log. PRICE_IN_PER_M y PRICE_OUT_PER_M fuerzan una tarifa para todos los proveedores, y la tabla no es una afirmación de lo que cobra tu propio contrato con el proveedor.

Antes de cada llamada al modelo el backend reserva la estimación máxima contra la solicitud, el agente y la organización, y luego registra el mayor entre el costo que reporta el runtime y su propio recálculo, de modo que no depende de la exactitud del runtime. El gasto se lee de un ledger en Postgres. /v1/estimate da un rango antes de ejecutar, nunca una cifra única. Límites:

ControlDónde se aplicaEfecto al excederse
Presupuesto de la organización (BUDGET_USD)Backend, antes de cada llamada al modeloLa tarea falla con un mensaje explícito y un evento; no se reanuda desde la API
Tope por solicitud (REQUEST_BUDGET_CAP_USD)BackendLa solicitud se pausa con budget.exceeded; subir el tope para continuar
Tope por agente (AGENT_BUDGET_USD)BackendEl agente se pausa; subir el tope para continuar
COST_CONFIRM_THRESHOLD_USDBackend, tras /v1/estimateUna persona confirma el costo estimado antes de ejecutar
MAX_PARALLEL_PER_ORGCola del backendLas llamadas esperan en una cola con prioridad
