Referencia de configuración

Toda la configuración de AI Workforce OS se lee de variables de entorno. Esta página lista las del backend (Go), el runtime de agentes (Python) y el frontend (Next.js), con el valor por defecto que fija el código. Es para quien instala u opera una instancia propia.

Cómo se carga la configuración#

El backend lee el entorno al arrancar y valida la combinación antes de abrir el puerto: si algo es incoherente, el proceso termina con un error que nombra la variable. El runtime lee sus variables cuando las usa. El frontend no lee nada en ejecución: sus valores quedan fijados al compilar.

  • Booleanos: true, false, 1, 0 y el resto de valores que acepta strconv.ParseBool. Un valor inválido aborta el arranque.
  • Enteros y duraciones: un valor ausente, no numérico o menor o igual que cero se sustituye por el valor por defecto. Las duraciones usan la sintaxis de Go (30s, 5m, 1h).
  • Importes en USD: 0 es válido y desactiva el tope correspondiente; un valor negativo o no numérico deja el valor por defecto. La excepción es BUDGET_USD, que necesita un valor mayor que cero.
  • Listas: valores separados por comas; se ignoran los espacios.

Nota

En las tablas, «Condicional» significa que la variable solo es obligatoria en combinación con otra (por ejemplo JWT_SECRET con AUTH_ENABLED=true). «No» significa que hay un valor por defecto o que la función queda desactivada.

Autenticación, CORS y proxy#

Con AUTH_ENABLED=false el backend funciona en modo demo: una organización fija y sin inicio de sesión. Con AUTH_ENABLED=true activa cuentas, JWT, RBAC y aislamiento por organización, y el org_id sale del token.

Con la autenticación activa, el arranque falla si JWT_SECRET tiene menos de 32 bytes, si falta DATABASE_URL o si ALLOWED_ORIGINS contiene *.

VariablePor defectoObligatoriaSignificado
AUTH_ENABLEDfalseNoActiva cuentas, JWT, RBAC y multi-tenencia. El compose de producción lo fija a true.
JWT_SECRETvacíoCondicionalClave de firma de los tokens de acceso; mínimo 32 bytes; obligatoria con AUTH_ENABLED=true. Rotarla invalida todas las sesiones.
ALLOWED_ORIGINSvacíoCondicionalOrígenes permitidos para CORS y WebSocket, separados por comas y sin barra final. Vacía sin autenticación equivale a *; vacía con autenticación, solo el mismo origen.
AUTH_COOKIE_SECUREtrueNoAtributo Secure de la cookie del refresh token. Solo se desactiva en desarrollo local con HTTP plano.
AUTH_COOKIE_NAMEwfai_refreshNoNombre de la cookie del refresh token. Cámbialo si varias instalaciones comparten host.
TRUSTED_PROXIESvacíoNoCIDR o IP de los proxies cuyo X-Forwarded-For se respeta (lo usan los límites de tasa). Un valor inválido aborta el arranque.
ENABLE_DEMO_RESETfalseNoRegistra POST /api/v1/demo/reset, que borra los datos de ejecución. Déjala en false en producción.

Atención

Con AUTH_ENABLED=false no hay inicio de sesión: cualquiera que alcance la URL controla la organización demo. No expongas ese modo a internet con datos o claves reales.

Recompensas y monedas#

El sistema de monedas premia el trabajo completado. REWARDS_RULES acepta un JSON que se aplica encima de las reglas por defecto, así que basta con incluir los campos que quieras cambiar.

Si el JSON tiene un valor inválido, el backend lo registra en el log y usa las reglas por defecto completas: nunca aplica una economía a medias.

VariablePor defectoObligatoriaSignificado
REWARDS_ENABLEDtrueNofalse, 0 u off desactivan por completo la obtención de monedas.
REWARDS_RULESvacíoNoJSON con reglas: enabled, base (S, M, L, XL), default_complexity, first_try_bonus_pct, rework_pct, project_base, project_per_task, project_max, min_project_tasks.
REWARDS_WELCOME_COINS1000NoMonedas de bienvenida que recibe cada organización una sola vez, la primera vez que abre la tienda o la oficina. 0 lo desactiva.

Runtime: proveedores de modelo y claves#

El runtime admite cinco proveedores: deepseek, anthropic, openai, kimi y custom (un endpoint compatible con OpenAI, por ejemplo vLLM u Ollama). Un proveedor cuenta como configurado cuando su clave (y, para custom, su URL base) está en el entorno. Sin ningún proveedor configurado, o con SIMULATION=true, el runtime usa el motor simulado: respuestas guionadas, sin claves y sin costo.

Ante un error transitorio (timeout, límite de tasa, 5xx) reintenta en el mismo proveedor y después pasa al siguiente permitido. ALLOWED_PROVIDERS es el techo del operador: ningún dato llega a un proveedor excluido, ni siquiera como respaldo. Cada organización puede restringirlo más desde sus ajustes, nunca ampliarlo, y puede guardar su propia clave de proveedor, que gana a la del entorno.

SIMULATIONfalseNotrue fuerza el motor simulado aunque haya claves.

Atención

Las claves de proveedor son secretos que cuestan dinero si se filtran. Pásalas por el entorno del servicio, nunca en una imagen ni en el repositorio.

Conexiones, sandbox, almacenamiento y push#

Sin CONNECTIONS_KEK no se puede guardar ninguna credencial real: la bóveda falla cerrada y solo funcionan las conexiones simuladas. La KEK es base64 de 32 bytes aleatorios; guárdala aparte de la base de datos, porque sin ella los secretos cifrados son irrecuperables.

El sandbox de código es opcional y necesita el servicio sandbox-runner, que recibe acceso al socket de Docker. Lee antes la página del modelo de seguridad.

Límites de tasa#

Los límites de tasa están integrados en el backend y no tienen variables de ajuste: por ejemplo, 10 intentos de inicio de sesión cada 15 minutos y 120 comandos por minuto. Los de autenticación se guardan en Redis si hay REDIS_URL, y en memoria del proceso si no.

Lo que sí se configura es TRUSTED_PROXIES. Solo la cabecera X-Forwarded-For de esos proxies sirve para identificar al cliente. Detrás de Caddy, indica la red del proxy: sin ella, todos los clientes comparten la IP del proxy y el mismo contador.

Frontend: argumentos de build#

El frontend se compila con salida standalone. Las variables NEXT_PUBLIC_* se incorporan al compilar como argumentos del Dockerfile (ARG); cambiarlas exige reconstruir la imagen.

Dejarlas vacías da el comportamiento recomendado para un solo dominio: la API en la ruta relativa /api/v1 y el WebSocket derivado de window.location.

Argumento de buildPor defectoObligatoriaSignificado
NEXT_PUBLIC_API_URLvacíoNoURL base absoluta de la API, por ejemplo https://app.example.com/api/v1. Vacía: ruta relativa.
NEXT_PUBLIC_WS_URLvacíoNoURL absoluta del WebSocket, por ejemplo wss://app.example.com/ws. Vacía: se deriva de window.location.
NEXT_PUBLIC_MOCKvacíoNoCon el valor true, el frontend funciona con datos simulados, sin backend.

Verificación de correo y cuentas de prueba#

Dos funciones opcionales de acceso, las dos requieren AUTH_ENABLED=true. La verificación de correo exige un SMTP que funcione: con EMAIL_VERIFICATION=true y sin SMTP válido el backend se niega a arrancar, de modo que un servidor a medio configurar no deja a nadie fuera.

Las cuentas de prueba permiten usar la app sin registrarse; cada una tiene su propia organización y deja de funcionar sola.

EMAIL_VERIFICATIONfalseLas cuentas nuevas deben abrir un enlace de un solo uso enviado a su correo antes de entrar. Requiere AUTH_ENABLED, UI_BASE_URL y SMTP_* (o EMAIL_DEV_LOG).
EMAIL_DEV_LOGfalseSolo desarrollo: los enlaces de verificación se escriben en el log en lugar de enviarse.
SMTP_HOSTvacíoServidor SMTP. Obligatorio con EMAIL_VERIFICATION, salvo que EMAIL_DEV_LOG esté activo.
SMTP_PORT465465 usa TLS implícito; 587 usa STARTTLS.
SMTP_TLStls con el puerto 465; starttls con otrotls, starttls o none (none solo para un relay local).
SMTP_USER / SMTP_PASSvacíoCredenciales del servidor SMTP; define las dos o ninguna.
SMTP_FROMvacíoRemitente, por ejemplo AI Workforce OS <no-reply@example.com>. Obligatorio con verificación por SMTP.
