Referencia de configuración

Toda la configuración se lee del entorno. El backend (Go) carga y valida sus variables al arrancar y se niega a iniciar con valores incoherentes; el runtime (Python) lee las suyas al usarlas; el frontend solo tiene argumentos de build. Los valores por defecto de esta página provienen del código.

Cómo se carga la configuración

El backend lee el entorno en config.Load y llama a Validate antes de arrancar. Los booleanos aceptan los valores de strconv.ParseBool (true, false, 1, 0...) y un valor inválido aborta el arranque. En las variables numéricas y de duración, un valor ausente, no numérico o menor o igual que cero se sustituye por el valor por defecto. Las duraciones usan la sintaxis de Go (30s, 5m, 1h). Las listas van separadas por comas.

En la columna Obligatoria, «Sí» significa que el proceso no arranca sin la variable; «Condicional» indica que depende de otra variable; «No» significa que hay un valor por defecto o que la función se desactiva.

Autenticación, CORS y proxy

Con AUTH_ENABLED=false el backend funciona en modo demo (organización fija, sin login). Con AUTH_ENABLED=true activa JWT, RBAC y aislamiento por organización: el org_id sale del token. Validate rechaza JWT_SECRET de menos de 32 bytes, la ausencia de DATABASE_URL y un asterisco en ALLOWED_ORIGINS.

AUTH_ENABLEDfalseNoActiva cuentas, JWT, RBAC y multi-tenencia. El compose de producción lo fija a true.
JWT_SECRETvacíoCondicionalClave de firma de los tokens de acceso; mínimo 32 bytes; obligatoria con AUTH_ENABLED=true. Rotarla invalida las sesiones.
ALLOWED_ORIGINSvacíoCondicionalLista de orígenes permitidos para CORS y WebSocket, sin barra final. Vacía sin auth equivale a *; vacía con auth, solo mismo origen. No admite * con auth.

AUTH_COOKIE_NAMEvacíoNoNombre de la cookie, para evitar colisiones entre stacks que comparten host.
TRUSTED_PROXIESvacíoNoCIDR o IP de proxies cuyo X-Forwarded-For se respeta (por ejemplo para el rate limiting). Un valor inválido aborta el arranque.

Recompensas y monedas

El sistema de monedas premia el trabajo completado. REWARDS_RULES permite sustituir las reglas con un JSON cuyos campos coinciden con los nombres de abajo; los valores inválidos se rechazan y el backend vuelve a las reglas por defecto en lugar de aplicar una economía a medias. REWARDS_WELCOME_COINS concede una sola vez monedas de bienvenida a cada organización en su primer uso.

{
  "enabled": true,
  "base": { "S": 5, "M": 10, "L": 20, "XL": 40 },
  "default_complexity": "M",
  "first_try_bonus_pct": 50,
  "rework_pct": 50,
  "project_base": 20,
  "project_per_task": 2,
  "project_max": 100,
  "min_project_tasks": 2
}
VariablePor defectoObligatoriaSignificado
REWARDS_ENABLEDtrueNofalse, 0 u off desactivan por completo la obtención de monedas.
REWARDS_RULESvacíoNoJSON con reglas: enabled, base (S, M, L, XL), default_complexity, first_try_bonus_pct, rework_pct, project_base, project_per_task, project_max, min_project_tasks.
REWARDS_WELCOME_COINS1000NoMonedas de bienvenida que recibe cada organización una única vez en su primer uso. 0 lo desactiva.
Consejo. El ejemplo muestra las reglas por defecto. Basta con incluir en REWARDS_RULES los campos que se quieran cambiar.

Runtime: proveedores de modelo y claves

El runtime exige al menos un proveedor configurado, salvo con SIMULATION=true. Soporta deepseek, anthropic y un endpoint compatible con OpenAI (custom). Ante error, timeout o límite de tasa reintenta y pasa al siguiente proveedor permitido. Con ALLOWED_PROVIDERS ningún dato llega a un proveedor excluido, ni siquiera como respaldo. Las claves de proveedor son secretos: no las incluya en imágenes ni en el repositorio.

Conexiones, correo, sandbox y almacenamiento

Sin CONNECTIONS_KEK no se puede guardar ninguna credencial real: el sistema falla cerrado, y las conexiones simuladas siguen funcionando. La KEK es base64 de 32 bytes aleatorios; CONNECTIONS_KEK_PREVIOUS permite descifrar claves de datos antiguas durante una rotación. El sandbox de código es opcional y requiere el servicio sandbox-runner, que recibe acceso al socket de Docker; lea antes la documentación de seguridad.

Límites de tasa

Los límites de tasa de autenticación y comandos están integrados en el backend y la configuración actual no expone variables para ajustarlos. Lo que sí se configura es TRUSTED_PROXIES: solo la cabecera X-Forwarded-For de esos proxies se usa para identificar al cliente, de modo que detrás de Caddy conviene indicar la red del proxy, y sin ella la IP del cliente será la del proxy.

Frontend: argumentos de build

El frontend se compila con output standalone. Las variables NEXT_PUBLIC_* se incorporan en tiempo de build como argumentos del Dockerfile (ARG), no se leen en ejecución. Dejarlas vacías produce el comportamiento recomendado de un solo dominio: rutas relativas /api/v1 y WebSocket derivado de window.location.

docker build \
  --build-arg NEXT_PUBLIC_API_URL=https://app.example.com/api/v1 \
  --build-arg NEXT_PUBLIC_WS_URL=wss://app.example.com/ws \
  -t aiworkforce-frontend ./frontend
Argumento de buildPor defectoObligatoriaSignificado
NEXT_PUBLIC_API_URLvacíoNoURL base absoluta de la API (por ejemplo https://app.example.com/api/v1). Vacía: ruta relativa.
NEXT_PUBLIC_WS_URLvacíoNoURL absoluta del WebSocket (wss://app.example.com/ws). Vacía: se deriva de window.location.
NEXT_PUBLIC_MOCKvacíoNotrue ejecuta el frontend con datos simulados, sin backend.

Verificación de correo y cuentas de prueba

Dos funciones opcionales de acceso. La verificación de correo exige SMTP funcional: con EMAIL_VERIFICATION=true y sin SMTP válido el backend se niega a arrancar, de modo que un servidor a medio configurar no deja a nadie fuera. Las cuentas de prueba permiten probar sin registrarse y caducan solas.

EMAIL_DEV_LOGfalseSolo desarrollo: los enlaces de verificación se escriben en el log en lugar de enviarse.
SMTP_HOSTServidor SMTP. Obligatorio con EMAIL_VERIFICATION salvo que EMAIL_DEV_LOG esté activo.
