Autenticación y multitenencia

AI Workforce OS puede correr abierto, con una organización fija, o con cuentas, roles y aislamiento por organización. Esta página describe el servicio de autenticación del backend en Go: cómo funcionan cuentas y sesiones, qué puede hacer cada rol y cómo Postgres hace cumplir la frontera entre organizaciones.

Dos modos: AUTH_ENABLED false y true

Con AUTH_ENABLED=false (el valor por defecto) no hay login. La API está abierta y cada solicitud usa una única organización demo fija. Está pensado para desarrollo local y demos, y el servidor registra una advertencia al arrancar. No lo expongas a una red.

Con AUTH_ENABLED=true la API exige un token de acceso bearer en las rutas protegidas, resuelve un rol en cada solicitud y limita todo acceso a la base de datos a la organización de quien llama. La validación de arranque rechaza la configuración si JWT_SECRET tiene menos de 32 bytes, si falta DATABASE_URL o si ALLOWED_ORIGINS contiene un comodín.

# Auth enabled
AUTH_ENABLED=true
JWT_SECRET=<at least 32 random bytes>
DATABASE_URL=postgres://...         # required with auth
MIGRATE_DATABASE_URL=postgres://... # owner/DDL role, runs migrations
DB_APP_ROLE=app_user                # default
ALLOWED_ORIGINS=https://app.example.com   # no wildcard when auth is on
TRUSTED_PROXIES=10.0.0.0/8          # honour X-Forwarded-For for IP limits
AUTH_COOKIE_SECURE=true             # default; false only for plain-http dev
AUTH_COOKIE_NAME=wfai_refresh       # optional override

Cuentas y registro

Registrarse crea en un solo paso un usuario, una organización nueva y una membresía de owner, y abre una sesión. La organización parte con el presupuesto por defecto configurado para organizaciones nuevas. Los correos se normalizan (recorte y minúsculas) antes de cualquier búsqueda o almacenamiento, de modo que Ana@Example.com y ana@example.com son la misma cuenta.

Las contraseñas se almacenan con Argon2id (64 MiB, 3 iteraciones, 2 carriles por defecto). Los hashes creados con parámetros más débiles se recalculan en el siguiente login correcto. La entrada se valida con estas reglas:

CampoRegla
emailSe recorta y pasa a minúsculas; máximo 254 caracteres; debe ser una dirección simple con un punto en el dominio
password10 a 128 caracteres; fuera de una lista corta de contraseñas comunes; distinta del correo o de su parte local; no un solo carácter repetido; al menos dos clases entre minúsculas, mayúsculas, dígitos y símbolos
name1 a 100 caracteres, sin caracteres de control
org_name2 a 100 caracteres, sin caracteres de control; el slug se deriva de él más un sufijo aleatorio

Login, bloqueo y límites de tasa

Los fallos de login se cuentan por cuenta. Tras cinco contraseñas erróneas la cuenta se bloquea 15 minutos y los intentos siguientes devuelven un error de bloqueo con la hora de desbloqueo. Los correos desconocidos se verifican contra un hash ficticio, de modo que una cuenta inexistente cuesta lo mismo que una contraseña errónea, lo que limita la enumeración de cuentas.

La limitación es por capas: un limitador por correo que no depende de si la cuenta existe y limitadores por IP en los endpoints sin autenticar. Los contadores viven en Redis cuando está disponible, por lo que sobreviven a reinicios, y en memoria en caso contrario. Los límites por IP solo respetan X-Forwarded-For de las direcciones listadas en TRUSTED_PROXIES. Los valores por defecto son:

LímitePor defectoClave
Intentos de login10 por 15 minCorreo (con hash), exista o no la cuenta
POST /login20 por 15 minIP del cliente
POST /register y /invitations/accept5 por horaIP del cliente
POST /refresh y /logout60 por 15 minIP del cliente
Endpoints autenticados de auth e invitaciones120 por minUsuario
Contraseñas erróneas antes del bloqueo5, bloqueo de 15 minCuenta

Sesiones: token de acceso y refresh rotatorio

Una sesión tiene dos partes. El token de acceso es un JWT firmado con HMAC y de vida corta (15 minutos por defecto) que lleva usuario, organización y rol, y se envía como bearer. El refresh token es un valor aleatorio opaco, válido 30 días por defecto, guardado en el servidor solo como hash SHA-256 y entregado en una cookie HttpOnly, SameSite=Strict (wfai_refresh) limitada a /api/v1/auth, con el atributo Secure activo por defecto. Nunca aparece en un cuerpo JSON.

Refresh y logout actúan sobre la cookie ambiental, así que exigen la cabecera propia X-WFAI-CSRF y rechazan solicitudes cross-site según Sec-Fetch-Site y Origin. Cada refresh rota el token dentro de una familia. Presentar un token ya usado revoca la familia completa, lo que detecta robos. Logout revoca la familia; logout-all revoca todos los refresh tokens del usuario en todas sus organizaciones.

POST /api/v1/auth/login
Content-Type: application/json

{"email":"ana@example.com","password":"...","org_id":"(optional)"}

200 OK
Set-Cookie: wfai_refresh=...; Path=/api/v1/auth; HttpOnly; SameSite=Strict; Secure
{"token_type":"Bearer","access_token":"...","expires_in":900,
 "user":{...},"org_id":"...","role":"owner"}

Roles y permisos (RBAC)

Cada membresía tiene un rol: owner, admin, member o viewer. Un rol es un conjunto de permisos con nombre recurso:acción, y cada rol es un superconjunto estricto del inferior. Por defecto el rol se vuelve a leer de la base de datos en cada solicitud, así que degradar o quitar a un miembro surte efecto de inmediato y no al expirar el token de acceso (la opción TrustTokenClaims cambia esto por ausencia de estado).

Los cambios de rol siguen dos reglas. Un owner puede asignar cualquier rol; un admin solo asigna y gestiona roles inferiores a admin; nadie puede otorgar un rol superior al suyo. El último owner no puede eliminarse. Los agentes nunca tienen permisos de aprobación como artifacts:approve.

RolAñade sobre el rol inferior
viewerSolo lectura: miembros, agentes, tareas, solicitudes, conversaciones, aprobaciones, informes, memorias, actividad, métricas, artefactos, archivos, habilidades, tienda
memberCrear solicitudes y tareas, escribir en conversaciones, escribir memorias, crear/editar/comentar/exportar artefactos, escribir archivos y habilidades, comprar en la tienda, leer conexiones
adminGestionar la organización, invitar y gestionar miembros, escribir agentes, gestionar tareas, decidir aprobaciones, leer la auditoría, gestionar conexiones y permisos, pausa y kill switch, aprobar/borrar artefactos, borrar archivos, revisar habilidades, borrar conversaciones
ownerEliminar la organización, facturación, liberar el kill switch, editar la política de aprobaciones (policy:manage)

Organizaciones, miembros y cambio de organización

Un usuario puede pertenecer a varias organizaciones, con un rol distinto en cada una. GET /me devuelve el usuario y la lista de organizaciones con nombre y rol. POST /switch-org abre una sesión nueva en otra organización a la que el usuario pertenece, y conviene descartar el refresh token anterior. Pedir una organización sin membresía devuelve forbidden.

Los miembros se listan, se agregan por correo (un usuario existente), se les cambia el rol y se eliminan solo dentro de la organización de quien actúa; los objetivos de otras organizaciones se reportan como no encontrados. Quitar a un miembro también revoca sus refresh tokens de esa organización.

Invitaciones

Admins y owners crean invitaciones para un correo y un rol que pueden asignar. El servidor guarda solo el SHA-256 del token de un solo uso y devuelve el texto plano una única vez, al crear. El servidor no envía correo: quien invita comparte el enlace, que el frontend sirve en /invite. Una invitación nueva a la misma dirección revoca la pendiente anterior, y los enlaces expiran a los 7 días por defecto.

Aceptar es público y recibe el token. Una persona nueva indica nombre y contraseña. Una cuenta existente debe demostrar la propiedad con su contraseña actual, con el mismo bloqueo que el login. Los tokens desconocidos, expirados, revocados y usados fallan sin revelar cuál es el caso. Si quien invitó fue degradado o eliminado, la invitación deja de funcionar. Creación, revocación y aceptación quedan en la auditoría, guardando solo el dominio del correo.

Aislamiento con row-level security de Postgres

Los roles deciden qué puede hacer un usuario; la row-level security decide qué filas existen para él. Cada tabla de tenant tiene una política tenant_isolation que compara org_id con app_current_org(), y FORCE ROW LEVEL SECURITY la aplica incluso al dueño de la tabla. Cada solicitud corre en una transacción que empieza con set_config('app.org_id', ..., true). El ajuste es local a la transacción, así que una conexión del pool no puede arrastrar un tenant a otra solicitud.

Falla cerrado: con app.org_id sin definir, ninguna fila es visible ni escribible. El servidor se conecta con credenciales de dueño y cambia a app_user en cada conexión (DB_APP_ROLE), un rol que no es superusuario, no tiene BYPASSRLS y no es dueño de ninguna tabla. El log de auditoría es de solo anexado para ese rol (UPDATE y DELETE revocados). Las migraciones corren con MIGRATE_DATABASE_URL, aparte.

-- One transaction per request, scoped to the caller's organization
SELECT set_config('app.org_id', '<org id>', true);   -- == SET LOCAL

CREATE POLICY tenant_isolation ON agents
  USING      (org_id = app_current_org())
  WITH CHECK (org_id = app_current_org());

Referencia de endpoints

El router de auth se monta en /api/v1/auth y el de invitaciones bajo el mismo prefijo. Los permisos se comprueban en un middleware antes del handler; el servicio vuelve a comprobar la membresía actual de quien actúa en cada operación sobre miembros.

EndpointAcceso
POST /api/v1/auth/register, /login, /refresh, /logoutPúblico (refresh y logout usan la cookie más X-WFAI-CSRF)
POST /api/v1/auth/invitations/acceptPúblico, token en el cuerpo
GET /api/v1/auth/configPúblico, indica si auth y registro están activos
GET /me, POST /logout-all, POST /switch-orgCualquier usuario autenticado
GET/POST/PATCH/DELETE /membersmembers:read, members:invite, members:manage; un miembro puede salirse solo
GET/POST/DELETE /invitationsmembers:read para listar, members:invite para crear y revocar
Consejo. Consulta la referencia de la API para la lista completa de rutas y el modelo de seguridad para el análisis de amenazas.
