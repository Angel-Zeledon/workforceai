Despliegue en producción

AI Workforce OS se despliega con un compose de producción independiente: Caddy termina TLS y enruta hacia el frontend (Next.js) y el backend (Go); el backend habla con el runtime de agentes (Python), Postgres y Redis. Esta guía cubre la instalación, la operación y el layout reducido que se usa para una demo en un solo servidor.

Topología

El archivo docker-compose.prod.yml es independiente: no se combina con el docker-compose.yml de desarrollo. Usa un solo dominio. Caddy envía /api/* y /ws al backend (puerto 8080 interno) y todo lo demás al frontend (puerto 3000 interno).

Solo Caddy publica puertos (80, 443 TCP y 443 UDP). Postgres, Redis, runtime, backend y frontend viven en la red internal, declarada con internal: true y por tanto sin salida a internet. El runtime se une además a la red egress para llamar a las APIs de los proveedores de modelo. Caddy usa la red edge más internal.

El frontend se construye con rutas relativas (/api/v1) y deriva la URL del WebSocket de window.location (wss:// bajo HTTPS), así que en un despliegue de un solo dominio no hace falta hornear variables NEXT_PUBLIC_*.

Requisitos

  1. Servidor Linux con Docker Engine y el plugin Docker Compose v2, con los puertos 80 y 443 abiertos en el firewall.
  2. Un dominio con registro DNS A (y AAAA si hay IPv6) que apunte al servidor. Let's Encrypt falla si el DNS aún no resuelve.
  3. Acceso a las imágenes en GHCR. Si los paquetes son privados, ejecute docker login ghcr.io con un token con permiso read:packages. Alternativa: construir localmente con --build.
  4. Al menos una credencial de proveedor de modelo para el runtime (ver la página de configuración).

Instalación paso a paso

Los comandos usan example.com como dominio y OWNER y TAG como marcadores. Todo el estado vive en volúmenes con nombre; el archivo .env.prod queda fuera de git (el .gitignore del repositorio ya ignora .env.*).

git clone <repo-url> && cd <repo>
cp .env.prod.example .env.prod
chmod 600 .env.prod

# Edit: DOMAIN, ACME_EMAIL, ALLOWED_ORIGINS, OWNER, TAG, provider keys...
$EDITOR .env.prod
Consejo. Si las contraseñas llevan caracteres especiales, DATABASE_URL y REDIS_URL se rompen porque las incluyen en la URL. Use secretos en hex o codifíquelos con percent-encoding.

Generar secretos y validar la configuración

Genere un valor distinto para POSTGRES_PASSWORD, REDIS_PASSWORD y JWT_SECRET. El backend exige que JWT_SECRET tenga al menos 32 bytes cuando la autenticación está activa. El compose de producción fija AUTH_ENABLED a true. Se recomienda definir también RUNTIME_TOKEN, un secreto compartido entre backend y runtime (el backend avisa si está vacío).

Las variables marcadas como obligatorias en el compose (DOMAIN, ACME_EMAIL, POSTGRES_PASSWORD, REDIS_PASSWORD, OWNER, TAG, JWT_SECRET, ALLOWED_ORIGINS, DEEPSEEK_API_KEY) hacen fallar el comando de validación si faltan.

openssl rand -hex 32   # repeat for POSTGRES_PASSWORD, REDIS_PASSWORD, JWT_SECRET and RUNTIME_TOKEN

# Validate before starting (fails if a required variable is missing)
docker compose -f docker-compose.prod.yml --env-file .env.prod config -q

Arranque y comprobación de salud

Cada servicio define un healthcheck y las dependencias usan condition: service_healthy, de modo que el orden de arranque es Postgres y Redis, runtime, backend, y por último frontend y Caddy. El backend expone /healthz y el runtime también. Caddy obtiene y renueva el certificado automáticamente.

C="docker compose -f docker-compose.prod.yml --env-file .env.prod"

$C pull          # option A: images published by CI
# $C build       # option B: build locally
$C up -d
$C ps            # every service should become healthy
curl -fsS https://example.com/ -o /dev/null && echo OK
$C logs -f backend

Actualizar, migraciones y rollback

Para actualizar, cambie TAG por un valor sha-<corto> publicado por CI y vuelva a levantar. Haga siempre un pg_dump antes de desplegar una versión con migraciones.

El backend aplica migraciones SQL embebidas al arrancar, solo hacia adelante (tabla schema_migrations, sin migraciones down). Si la versión nueva falla y el esquema ya cambió, hay dos caminos: restaurar el dump previo y volver al TAG anterior (se pierden los datos escritos después), o desplegar una migración correctiva nueva, preferible si ya hay datos nuevos. Si la migración solo añadió columnas o tablas, el TAG anterior suele seguir funcionando sin tocar la base.

# 1) backup (see Backups)
# 2) point to the new tag
sed -i 's/^TAG=.*/TAG=sha-<NEW>/' .env.prod
$C pull
$C up -d

# Rollback without schema changes: restore the previous TAG
sed -i 's/^TAG=.*/TAG=sha-<PREVIOUS>/' .env.prod
$C pull && $C up -d

# Applied migrations
$C exec postgres psql -U workforce -d workforce -c 'select * from schema_migrations order by applied_at'

Backups y restauración de Postgres

Postgres es el dato maestro. Redis guarda AOF en el volumen redisdata y debe tratarse como caché y cola. Programe el pg_dump con cron, copie los archivos fuera del servidor y pruebe la restauración al menos una vez.

mkdir -p backups
$C exec -T postgres sh -c 'pg_dump -U "$POSTGRES_USER" -d "$POSTGRES_DB" -Fc' \
  > backups/workforce-$(date +%F-%H%M).dump

# Restore
$C stop backend
$C exec -T postgres sh -c 'dropdb -U "$POSTGRES_USER" --if-exists "$POSTGRES_DB" && createdb -U "$POSTGRES_USER" "$POSTGRES_DB"'
$C exec -T postgres sh -c 'pg_restore -U "$POSTGRES_USER" -d "$POSTGRES_DB" --no-owner' < backups/FILE.dump
$C start backend
Consejo. docker compose down conserva los volúmenes. No use -v salvo que quiera borrar los datos.

Checklist de salida a producción

  1. DNS apunta al servidor, 80 y 443 están abiertos y docker compose ps solo muestra puertos publicados en caddy.
  2. .env.prod tiene permisos 600 y está fuera de git.
  3. JWT_SECRET, POSTGRES_PASSWORD y REDIS_PASSWORD son únicos y aleatorios (32 bytes hex o más).
  4. ALLOWED_ORIGINS es exactamente https://example.com; AUTH_ENABLED es true; ENABLE_DEMO_RESET es false; SIMULATION es false.
  5. Hay al menos un proveedor de modelo válido, ALLOWED_PROVIDERS refleja la política de datos de la empresa y BUDGET_USD está definido.
  6. TAG apunta a un sha-<corto> concreto (no latest) que pasó el CI.
  7. Todos los servicios están healthy, el login funciona y el WebSocket conecta en wss://example.com/ws.
  8. El backup de Postgres está programado y la restauración se probó.
  9. Los logs rotan (json-file, 10 MB por 5 archivos, ya configurado) y los límites de memoria y CPU se ajustan al host.
Consejo. El compose actual solo pasa al runtime DEEPSEEK_API_KEY, ANTHROPIC_API_KEY, MODEL, RUNTIME_TOKEN y ALLOWED_PROVIDERS, y DEEPSEEK_API_KEY es obligatoria. Para usar un endpoint custom u otras variables del runtime hay que añadirlas al servicio agent-runtime del compose.

Publicación de imágenes en CI

El workflow .github/workflows/ci.yml compila y prueba backend, runtime y frontend, ejecuta govulncheck y npm audit (no bloqueantes), hadolint, un smoke test y los E2E con Playwright. En un push a main, el job publish sube a GHCR las tres imágenes (aiworkforce-backend, aiworkforce-agent-runtime, aiworkforce-frontend) con los tags sha-<corto> y latest, usando el GITHUB_TOKEN con permiso packages: write.

En el repositorio hay que permitir que el GITHUB_TOKEN escriba paquetes y, tras la primera publicación, enlazar los paquetes al repositorio y ajustar su visibilidad. Las variables de repositorio NEXT_PUBLIC_API_URL y NEXT_PUBLIC_WS_URL deben quedar sin definir en un despliegue de un solo dominio.

Layout reducido en un solo servidor

El directorio deploy/vps contiene el layout que se usa para una demo pública en un servidor compartido que ya tiene un Caddy propio dueño de los puertos 80 y 443. Allí el compose no publica ningún puerto: los servicios de borde (backend, frontend y la landing estática) se unen a la red del Caddy existente con alias únicos, y el resto permanece en una red privada.

Es una configuración de demo, no de producción: el runtime corre en modo SIMULATION (sin claves ni costo), no hay Postgres ni Redis (almacenamiento en memoria), AUTH_ENABLED es false y ENABLE_DEMO_RESET es true. El frontend se construye con NEXT_PUBLIC_API_URL y NEXT_PUBLIC_WS_URL absolutos, y el sitio de la app añade X-Robots-Tag noindex. Las rutas /api/* y /ws van al backend y lo demás al frontend, igual que en el Caddyfile de producción. El script deploy.sh hace pull, build con baja prioridad y up -d --wait.

example.com        -> landing (static)
app.example.com    -> /api/* and /ws -> backend:8080 ; rest -> frontend:3000
(existing Caddy terminates TLS; this project publishes no ports)
