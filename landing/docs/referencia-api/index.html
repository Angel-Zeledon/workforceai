Referencia de la API

El backend en Go expone una API REST bajo /api/v1 y un WebSocket en /ws. Esta referencia resume la autenticación, las convenciones y las rutas principales tal como están registradas en el router; los cuerpos de ejemplo son representativos y no exhaustivos.

URL base y versionado

Todas las rutas REST cuelgan de /api/v1; la versión forma parte de la ruta. El WebSocket (/ws) y el health check raíz (/healthz) están fuera de ese prefijo. Los cuerpos son JSON (UTF-8), salvo las subidas de archivos del drive, que usan el cuerpo crudo.

Con AUTH_ENABLED=false (modo demo) no se exige autenticación y todo opera sobre una organización fija. Con autenticación activa, todas las rutas excepto /healthz, /auth/* y el callback OAuth exigen un token. Los ejemplos usan localhost:8080; sustituye por tu host.

# Base URL (local default)
http://localhost:8080/api/v1
# WebSocket (outside /api/v1)
ws://localhost:8080/ws

# Health (no auth)
curl http://localhost:8080/healthz
# {"status":"ok","runtime":"up","runtime_mode":"simulation"}

Autenticación

El inicio de sesión devuelve un token de acceso (JWT, 15 minutos por defecto) que se envía en la cabecera Authorization: Bearer. El token de refresco nunca va en el cuerpo JSON: se guarda en una cookie HttpOnly y SameSite=Strict llamada wfai_refresh, limitada a la ruta /api/v1/auth. Los endpoints que usan esa cookie (refresh y logout) exigen además la cabecera X-WFAI-CSRF.

La organización sale del token, nunca de un parámetro. Los roles son owner, admin, member y viewer, y cada ruta exige un permiso concreto. El WebSocket acepta el token como ?access_token=.

# Log in: the access token is in the body, the refresh token in an HttpOnly cookie
curl -i -X POST http://localhost:8080/api/v1/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"you@example.com","password":"<password>"}'
# {"token_type":"Bearer","access_token":"<token>","expires_in":900,
#  "expires_at":"...","user":{...},"org_id":"<org id>","role":"owner"}

# Call the API with the access token
curl http://localhost:8080/api/v1/agents -H 'Authorization: Bearer <token>'

# Renew the session (cookie + CSRF header)
curl -X POST http://localhost:8080/api/v1/auth/refresh \
  -b 'wfai_refresh=<cookie value>' -H 'X-WFAI-CSRF: 1'
Método y rutaDescripción
POST /auth/registerCrea organización y usuario owner. Cuerpo: email, password, name, org_name.
POST /auth/loginInicia sesión. Cuerpo: email, password, org_id opcional.
POST /auth/refreshRota el refresh token (cookie + X-WFAI-CSRF) y devuelve un nuevo token de acceso.
POST /auth/logoutCierra la sesión actual y borra la cookie. Responde 204.
POST /auth/logout-allRevoca todas las sesiones del usuario.
POST /auth/switch-orgNueva sesión en otra organización. Cuerpo: org_id.
GET /auth/me, GET /auth/configUsuario actual; configuración pública (si hay login).
GET/POST /auth/members, PATCH/DELETE /auth/members/{id}Listar, agregar, cambiar el rol o quitar miembros.
GET/POST /invitations, DELETE /invitations/{id}Gestión de invitaciones. POST /auth/invitations/accept las acepta.

Errores, límites y convenciones

Los errores devuelven JSON con un código HTTP significativo. La mayoría de las rutas usan {"error": "mensaje"}; las de conexiones y controles agregan un campo code estable; las rutas de autenticación y las fallas de permisos usan {"error": {"code", "message"}}. Un 500 no expone el detalle interno.

No hay paginación global. Cada listado define sus propios parámetros: GET /activity acepta limit (100 por defecto, máximo 1000); GET /conversations/{id}/messages acepta limit (máximo 200) y before, y publica las cabeceras X-Has-More y X-Next-Before; los chats y el historial usan limit y offset; la memoria acepta limit y q. Los cuerpos JSON están limitados a 1 MiB por defecto (413 al excederlo). Las rutas de autenticación tienen límites de tasa por IP (429).

CódigoSignificado
400Cuerpo o parámetros inválidos.
401Falta el token o es inválido o expiró.
403El rol no tiene el permiso, o falla la verificación CSRF.
404Recurso inexistente en tu organización.
409Conflicto de estado (por ejemplo, una versión esperada distinta).
413Cuerpo demasiado grande.
429Límite de tasa de autenticación.
Consejo. POST /messages, POST /shop/purchases y otras operaciones con efectos aceptan Idempotency-Key; un reintento devuelve el primer resultado con la cabecera Idempotent-Replayed.

Peticiones, chat, tareas y reportes

POST /requests es asíncrono: responde 202 con el request_id y el avance llega por WebSocket. budget_cap_usd es opcional y fija un tope duro para esa petición.

# Submit a request (asynchronous: 202 + id, progress arrives over WebSocket)
curl -X POST http://localhost:8080/api/v1/requests \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"text":"Prepare a $50,000 proposal for ACME","budget_cap_usd":5}'
# 202 {"request_id":"<id>"}

# Chat message to the office (idempotent with the header)
curl -X POST http://localhost:8080/api/v1/messages \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: 7d1e...' \
  -d '{"conversation":"office","text":"Who is free today?"}'
# 202 turn object; replies arrive as chat.message events

POST /requestsCrea una petición. Cuerpo: text, budget_cap_usd opcional.
GET /requests, GET /requests/{id}Listar y ver el detalle (tareas y costo).
GET /requests/{id}/cost, /estimateCosto acumulado y estimación previa.
POST /requests/{id}/confirm, PUT /requests/{id}/budgetConfirmar una estimación; cambiar el tope.
POST /messagesMensaje de chat. Cuerpo: conversation (office por defecto), text, attachments.
GET /conversations, GET /conversations/{id}/messagesConversaciones y mensajes.
POST /conversations/{id}/messagesPublicar en una conversación concreta.
GET /tasks, GET /tasks/{id}Tareas; filtros agent_id y status.
GET /tasks/{id}/intervention, POST /tasks/{id}/steer, /reassignIntervenir una tarea en curso.

Aprobaciones y agentes

Decidir una aprobación es una acción privilegiada: solo admin u owner. Con aprobar se puede pedir además un permiso permanente (always_allow) para acciones internas y reversibles. Una aprobación puede exigir dos personas distintas.

# List pending approvals
curl 'http://localhost:8080/api/v1/approvals?status=pending' \
  -H 'Authorization: Bearer <token>'

# Approve (admin or owner)
curl -X POST http://localhost:8080/api/v1/approvals/<id>/decision \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"decision":"approve","note":"ok"}'
# 200 the updated approval; "decision" is "approve" or "reject"
Método y rutaDescripción
GET /approvalsLista; filtro status (pending, approved, rejected).
POST /approvals/{id}/decisionCuerpo: decision (approve o reject), note, always_allow, always_allow_any_agent, always_allow_days.
POST /approvals/batchDecidir varias aprobaciones de un proyecto.
GET /agents, GET /agents/{id}, GET /agents/{id}/detailAgentes: estado, herramientas, permisos y autonomía.
GET/PUT /agents/{id}/profile, GET /agents/{id}/tracesPerfil de trabajo versionado y trazas de razonamiento.
GET /agents/{id}/memory, DELETE /agents/{id}/memory/{docId}Memoria a largo plazo.
GET /role-templates, POST /agents/from-templateContratar un agente desde una plantilla.
PUT /agents/{id}/budget, POST /agents/{id}/controlPresupuesto y pausa o reanudación.

Proyectos y skills

Un proyecto es un plan de varios nodos con presupuesto. El ciclo es crear un borrador, editar el plan, estimar y validar, y lanzar. Las skills son instrucciones reutilizables, versionadas y con revisión antes de quedar activas.

# Create a draft project, then launch it
curl -X POST http://localhost:8080/api/v1/projects/draft \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{ ...project fields... }'
curl -X POST http://localhost:8080/api/v1/projects/<id>/launch \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' -d '{}'
Método y rutaDescripción
GET /projects, POST /projects/draft, POST /projects/from-templateListar y crear borradores.
GET /projects/{id}, /snapshot, /health, /approvalsEstado, salud y aprobaciones del proyecto.
PATCH /projects/{id}/plan, POST /estimate, /validate, /launchEditar, estimar, validar y lanzar.
POST /projects/{id}/control, PUT /projects/{id}/budgetControlar la ejecución y fijar el presupuesto.
POST /projects/{id}/nodes/{nodeId}/retry, /skip, /replanRecuperar un nodo.
GET/POST /project-templates, GET/PUT/DELETE /project-templates/{id}Plantillas con versiones.
GET/POST /skills, GET/PUT /skills/{id}Catálogo y edición de skills.
POST /skills/{id}/submit, /review, /disableFlujo de revisión; review y disable requieren permiso de revisor.
GET/PUT/DELETE /agents/{id}/skills[/{skillId}]Asignar skills a un agente.

Tienda, recompensas y drive

Las tareas y proyectos terminados pagan monedas una sola vez. La tienda gasta monedas de forma atómica y auditada. El drive guarda los archivos de la organización con versiones, papelera y permisos.

curl http://localhost:8080/api/v1/rewards/wallet -H 'Authorization: Bearer <token>'
curl -X POST http://localhost:8080/api/v1/shop/purchases \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"item_id":"<item id>","idempotency_key":"<unique key>"}'

Conexiones, controles y ajustes

Las conexiones guardan credenciales cifradas de servicios externos; sin CONNECTIONS_KEK no se pueden guardar credenciales reales. Los controles permiten pausar agentes, poner la organización en solo lectura o activar un kill switch.

# Pause or resume one agent
curl -X POST http://localhost:8080/api/v1/agents/<id>/control \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"action":"pause","drain":"graceful","reason":"maintenance"}'

# Organization kill switch (level: none | freeze | lockdown)
curl -X POST http://localhost:8080/api/v1/org/controls/kill-switch \
  -H 'Authorization: Bearer <token>' -H 'Content-Type: application/json' \
  -d '{"level":"freeze","reason":"incident"}'

GET /connection-providers, GET/POST /connectionsProveedores disponibles y conexiones.
PATCH /connections/{id}, PUT /connections/{id}/credentialEditar y guardar la credencial (solo escritura).
POST /connections/{id}/oauth/start, /testIniciar OAuth y probar la conexión.
GET /connections/oauth/callbackCallback público de OAuth, verificado por un estado de un solo uso.
GET/PUT /org/controls, POST /org/controls/kill-switch, /releaseModo solo lectura y kill switch (none, freeze, lockdown).
GET/PUT /org/operating-hours, /org/anomaly-settingsHorario operativo y ajustes de anomalías.
GET/PUT /org/settings, GET /onboarding, POST /onboardingAjustes de la organización y onboarding.

WebSocket y health

GET /ws abre el canal de eventos de la organización. Al conectar envía hello con la lista de agentes y luego cada evento de dominio. El cliente solo lee: el servidor ignora los mensajes que recibe, no hay suscripciones por tema ni replay. Si el token expira, el servidor cierra con el código 4401 y el cliente debe reconectar con un token nuevo.

GET /healthz y GET /api/v1/healthz no requieren autenticación. Devuelven status, runtime (up o down) y, si el runtime responde, runtime_mode (simulation o live).

# Browsers cannot set headers on a WebSocket: pass the token in the query string
wscat -c 'ws://localhost:8080/ws?access_token=<token>'
